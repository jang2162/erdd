# 워크트리 작업 흐름 — 만들고, 워커를 띄우고, 병합한다

**코드 변경 작업은 항상 워크트리에서 한다. 병렬 작업이든 단일 작업이든 예외 없다.**
그리고 **워크트리 안의 실제 작업은 Orca 터미널 워커가 한다** — 메인 세션은 디스패치·판정·병합만 한다.

요약과 「반드시 지킬 것」은 `CLAUDE.md` 의 「워크트리 작업 (요약)」 절에 있다.
여기에는 **절차와 실측 노하우**가 있다.

---

## 0. 왜 워크트리인가

**최상위 체크아웃(`/Users/jang2162/IdeaProjects/ERDD`)은 혼자 쓰는 작업 공간이 아니라 공유 자원이다.**
IDE, 실행 중인 dev 서버(`tsx watch`·vite 는 세션을 넘어 살아남는다), 다른 에이전트 세션이 동시에
그 디렉터리를 보고 있다. 최상위의 `HEAD` 를 옮기면 그것들이 전부 영향을 받는다.

⚠️ **「지금은 나 혼자 작업하니 최상위에서 브랜치를 갈아타도 된다」가 반복된 이탈이다.**
동시 작업이 하나도 없어 보여도 사람이 켜 둔 IDE·서버는 남아 있다.

최상위에서 허용되는 것은 **읽기 작업**(`status`·`log`·`diff`·`show`·`fetch`)과 현재 주 트랙 위의
커밋뿐이다. 체크아웃이 꼭 필요하면 **먼저 사용자에게 확인**을 받는다.

## 1. 워크트리 만들기

```bash
git worktree add -b feat/<작업명> .worktrees/feat-<작업명> main
```

- **위치는 `.worktrees/<브랜치-슬러그>/`** — 저장소 루트 하위이고 gitignore 된다.
  저장소 바깥이나 임의 경로에 만들지 마라. 다른 에이전트가 찾지 못한다.
- **브랜치를 함께 만든다.** 이미 다른 워크트리가 체크아웃한 브랜치는 git 이 거부한다.
- ⚠️ **기준 브랜치는 로컬 `main` 을 명시한다.** 생략하면 현재 `HEAD`(= 진행 중인 주 트랙)를 물고,
  `origin/main` 을 쓰면 뒤처진 옛 커밋을 잡는다(수십 커밋 뒤처진 상태로 시작한 적이 있다).
- **하나의 작업 = 하나의 워크트리.** 여러 작업을 한 워크트리에서 브랜치 갈아타며 처리하지 않는다.
- **만들기 전에 `git worktree list` 로 같은 작업의 워크트리가 이미 있는지 본다.**
  있으면 새로 만들지 말고 그것을 쓴다.

### 생성 직후 세팅

- **`pnpm install` 을 워크트리 안에서 직접 실행한다.** `post-checkout` 훅은 새 워크트리에서 자동으로
  돌지 않을 수 있다. **새 런타임 의존성이 붙은 트랙은 설치 전에는 타입이 implicit any 로 깨진다.**
- **포트·DB 를 트랙별로 가른다.** 같은 포트를 물면 먼저 뜬 워크트리만 살고 나머지는 조용히 죽거나
  남의 서버에 붙는다. 공유 `erdd_test` 를 두 트랙이 함께 쓰면 테스트가 서로의 데이터를 지운다.
  할당표와 환경 변수는 [setup.md](setup.md) 「워크트리에서는 포트·DB 를 트랙별로 가른다」 절.
- **격리 DB 는 미리 만들고 마이그레이션을 적용해 둔다.**

### 정리

```bash
git worktree remove .worktrees/<...>
```

- 디렉터리를 `rm -rf` 로 지웠다면 `git worktree prune` 을 함께 돌린다.
- ⚠️ **지우기 전에 컨테이너·볼륨을 정리한다.** compose `down` 은 컨테이너만 내리고 named volume 을
  남기므로, 워크트리를 지우면 볼륨이 고아로 쌓인다. 워크트리 디렉터리 안에서 `down -v` 까지 돌린 뒤
  제거한다. 볼륨을 직접 지울 때는 **접두사를 확인해라** — 최상위 체크아웃의 공유 DB 볼륨
  (`erdd-db-1`)을 함께 날리기 쉽다.

## 2. 메인 세션과 워커의 역할 분리

**메인 세션은 워크트리를 만들고, 그 안의 실제 작업은 Orca 로 띄운 Claude 세션이 한다.**
메인 세션이 워크트리에 들어가 직접 파일을 고치지 않는다.

| 누가 | 무엇을 |
|---|---|
| **메인 세션** | 워크트리 생성, 워커·리뷰어를 띄우고 브리프를 쓰는 것, 받은 보고를 두고 무엇을 고치고 무엇을 이월할지 **판정**, main 병합, 정본 문서 갱신 |
| **워커** | 구현, 리뷰, 테스트 실행, 구분력 실증, 스모크 — **실행은 전부 워크트리 안에서** 워커가 한다 |

- **「리뷰」는 리뷰어를 띄우는 것이지 메인 세션이 코드를 뜯어보는 것이 아니다.** 보고가 미검증
  주장인 것은 맞지만 그 검증도 워커에게 시킨다 — 구현자와 리뷰어가 **각각 독립적으로** 구분력을
  실증하므로 두 소스가 이미 교차 검증된다. **둘이 갈리거나 한쪽이 「실패하지 않았다」고 보고할 때만**
  제3의 워커를 띄워 재현시킨다. 컨트롤러의 재실증이 워커·리뷰어 보고를 뒤집은 사례는 없다.
- ⚠️ **이 분리는 사고를 막는다.** 메인 세션의 셸은 `cd` 가 유지되므로 최상위와 워크트리를 오가다
  **어디에 있는지 착각하기 쉽다**(최상위에 있는 줄 모르고 워크트리 기준으로 명령을 돌린 적이 있다).
  메인 세션이 워크트리에서 아무것도 쓰지 않으면 이 사고 자체가 성립하지 않고, 워커가 도는 중에
  같은 파일을 만져 워커의 작업을 덮어쓰는 경합도 함께 사라진다.
- **트리거는 워크트리다.** 병렬 트랙인지, 태스크를 순차로 도는지, 워커가 하나인지는 따지지 않는다.
  태스크마다 워커를 띄우는 워크플로도 마찬가지다 — 구현자·리뷰어를 Orca 터미널 워커로 띄운다.
- **판단 지점은 「워크트리를 만들 때」가 아니라 「일을 시작할 때」다.** 워크트리만 만들어 놓고 메인
  세션이 직접 고치거나 서브에이전트를 써 버리는 것이 가장 흔한 이탈이다. 그래서
  **워크트리를 만들기 전에 `orca status --json` 부터 실행한다.**
- **Orca 환경이 아니거나 오케스트레이션이 불가하면** 워크트리 + 서브에이전트로 진행한다.

## 3. Orca 워커를 띄운다

방식은 외우지 말고 `orca skills get orchestration` 으로 버전 맞춤 가이드를 읽어라
(플래그·서브커맨드가 릴리스마다 바뀐다).

**환경 확인:** `orca status --json` 이 running runtime 을 보이면 Orca 환경이다.
CLI 실행자는 `ORCA_CLI_COMMAND` 가 있으면 그 값, 없으면 macOS·일반은 `orca`,
**Linux 는 `orca-ide`**(리눅스에서 bare `orca` 는 GNOME 스크린리더로 붙는다).

**감독(supervised) vs 완전 위임(handoff):** 완료를 기다려 리뷰·병합하면 supervised
(`task-create` + 주입 + `check --wait`). 소유권을 넘기고 안 지켜보면 full handoff.

### 워커 하나를 띄우는 단계는 다섯이다 — ④를 빼먹지 마라

```bash
orca worktree list --json                                   # .worktrees/* 도 id 로 나온다
orca terminal create --worktree id:<fullId> --command "claude"
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000
orca orchestration worker-start --task <task_id> --terminal <handle> --json
orca terminal read --terminal <handle> --json               # ④ 제출 확인 — 생략 금지
orca orchestration check --wait --types worker_done,escalation,decision_gate
```

### ⚠️ 주입의 성공 응답은 「전송」까지만 보증한다. 제출은 따로 확인해야 한다

`worker-start` 의 `stage: input_accepted` 도 `dispatch --inject` 의
`dispatch_input.state: accepted` 도 **터미널에 바이트를 썼다**는 뜻이지 TUI 가 그 입력을
**제출했다**는 뜻이 아니다. 실패하면 브리프가 입력창에 텍스트로 남은 채 워커는 아무것도 하지
않는데, **`check --wait` 는 15분을 조용히 기다리다 `timedOut` 으로 끝나므로 워커가 죽은 것처럼
보이지도 않는다.**

**판정 기준은 `Ctx Used` 다 — `0.0%` 면 무조건 미제출이다.** 미제출은 두 형태이고 대응이 다르다.

- **(a) 입력창(`❯`)에 브리프 텍스트가 그대로 보인다** — 바이트는 들어갔고 Enter 만 흡수됐다.
  엔터만 보내 제출시키고, **다시 읽어 입력창이 비었는지 확인한 뒤에** 대기로 넘어간다.
  ```bash
  orca terminal send --terminal <handle> --text "" --enter --json
  orca terminal read  --terminal <handle> --json      # 입력창이 비어 있어야 한다
  ```
- **(b) 입력창도 비어 있다(시작 화면만 있고 `Ctx Used: 0.0%`)** — 바이트가 **아예 안 들어갔다.**
  보낼 Enter 가 없으므로 (a) 의 방법이 통하지 않는다. **파일 경유로 간다**(아래).

`worker-read` 로도 같은 것을 본다 — `terminal.tail` 에 프롬프트가 그대로 있고 `Ctx Used: 0.0%` 면
미제출이다. 제출되면 `source` 가 `terminal` → `transcript` 로 바뀌고 실제 도구 호출이 보인다.

### 🔥 파일 경유가 기본이다 — 예방책을 지켜도 실패한다

터미널 생성과 주입을 분리하는 위 순서를 **정확히 따라도** 네 워커 모두 컨텍스트 0.0% 로 아무것도
받지 못한 적이 있다. **긴 한국어 멀티라인 브리프에서는 실패 쪽이 기본값에 가깝다** — 처음부터
파일 경유로 가는 편이 빠르다. 브리프를 워크트리 루트에 파일로 쓰고 짧은 한 줄만 보낸다.
여러 줄이 TUI 에 흡수되는 문제 자체가 사라진다.

```bash
orca terminal send --terminal <handle> \
  --text "워크트리 루트의 BRIEF.md 를 읽고 그 지시를 그대로 수행해라." --enter --json
orca terminal read --terminal <handle> --json      # Ctx Used 가 0.0% 를 벗어나야 제출된 것
```

⚠️ **파일 경유로 우회하면 워커가 `worker_done` 을 보낼 수 없다.** `worker-start` 가 주입하는
lifecycle preamble 에 `taskId`·`dispatchId` 가 들어 있는데 `terminal send` 에는 그것이 없다.
워커는 일을 정상적으로 마치고도 보고할 방법이 없어 화면에만 결과를 남긴다(실제로 한 번 그렇게 잃었다).
**브리프 파일 끝에 완료 보고 명령을 ID 와 함께 박아 둬라.**

```bash
D=$(orca orchestration dispatch-show --task <task_id> --json \
    | python3 -c "import sys,json; print(json.load(sys.stdin)['result']['dispatch']['id'])")
# 브리프 끝에 아래를 적는다:
#   orca orchestration send --type worker_done --subject "<요약>" --body "<본문>" \
#     --task-id <task_id> --dispatch-id $D --outcome succeeded --json
```

### 🔥 워커에게 보내는 문자열을 셸이 한 번도 해석하지 않게 해라

heredoc 만의 문제가 아니다 — `task-create --spec "…"` · `send --body "…"` ·
`terminal send --text "…"` 전부 같다. **zsh 는 큰따옴표 안에서도 백틱을 명령 치환으로 실행한다.**
`--spec` 안의 백틱 경로가 빈칸이 된 채 워커에게 간 적이 있고, 하필 사라진 것이
**「이 파일은 건드리지 마라」의 파일 이름 둘**이라 그대로 뒀으면 다른 트랙과 같은 파일을 고쳤을 것이다.

- **쓰는 법:** 본문을 파일에 먼저 쓰고 `"$(cat /tmp/brief.txt)"` 로 넘긴다.
- **검증(생략 금지):** 보낸 뒤 `orca orchestration task-list --json` 으로 **실제로 간 문장을
  되읽어** 핵심 문자열을 grep 한다. `--spec` 은 파일과 달리 눈에 안 보여 이 확인이 더 중요하다.
- ⚠️ **브리프 heredoc 은 반드시 따옴표로 막아라 — `<<'BRIEF'`.** 따옴표 없는 `<<BRIEF` 는
  `$`·백틱·글롭·히스토리 확장(`!`)을 전부 해석한다. 브리프의 한 낱말이 셸 빌트인으로 확장돼
  **그 출력 수백 줄이 브리프 한가운데 끼어든** 적이 있고, `[a, b]` 꼴이 글롭으로 해석돼
  **그 줄만 조용히 사라진** 적도 있다(핵심 수정 방법이 담긴 줄이었다). **오류가 나지 않고 조용히
  짧아진다.** 쓴 뒤에는 줄 수와 핵심 문자열을 grep 으로 확인해라.
- ⚠️ **`${VAR:+--flag "$VAR"}` 같은 조건부 확장은 두 인자가 아니라 한 인자로 붙는다** —
  `check ${D:+--ack "$D"} --wait` 가 `Unknown flag` 로 즉시 죽는다. 분기해 두 줄로 써라.
- ⚠️ **셸 변수는 `orca` 호출 사이에 살아남지 않는다**(작업 디렉터리는 유지된다). 워크트리 id 같은
  긴 값을 변수에 담아 다음 호출에서 쓰면 **빈 문자열이 들어가 `worker-start` 가 조용히 실패한다**
  (응답의 `stage` 가 `null` 로 온다 — 오류가 아니라 빈 성공처럼 보인다). 파일에 적어 두고
  `$(cat …)` 로 읽어라.

### 대기와 응답 처리

- ⚠️ **`--json` 출력은 NDJSON 이고 keepalive 가 섞인다.** `check --wait` 는 15초마다
  `{"_keepalive":true,…}` 를 한 줄씩 내고 **마지막 실제 결과는 여러 줄 pretty-print** 다.
  통째로 파싱하면 `Extra data` 로 깨지고 줄 단위 파싱은 마지막 결과를 놓친다. `raw_decode` 로
  스트리밍 파싱해 `_keepalive` 가 아닌 마지막 객체를 취해라.
- **`timedOut`/`count:0` 은 워커 실패가 아니라 체크포인트다.** 긴 작업은 15~60분이 보통이다.
  `worker_done`/`escalation` 을 받거나 터미널이 사라지지 않는 한 rolling wait 를 계속한다.
- ⚠️ **`runtime_unavailable` 도 워커 실패가 아니다.** 코디네이터의 **대기 연결만** 끊긴 것이고
  워커 프로세스는 그대로 돈다. 재시작하지 말고 확인부터 해라 — `orca status --json`,
  `worker-show --dispatch`, `worker-read --dispatch`(`source: transcript` + terminal `running` 이면
  살아 있다), 그리고 **워크트리의 `git log`**(워커가 이미 커밋했는지). 살아 있으면 `check --wait` 를
  다시 걸면 된다. 워커를 죽이고 재디스패치하면 진행 중인 작업을 버리게 된다.
- ⚠️ **받은 Delivery 는 반드시 `--ack` 하라.** `check` 는 가장 오래된 Delivery 배치를
  `--ack <delivery_id>` 할 때까지 **그대로 재생한다.** ack 없이 다음 `check --wait` 를 걸면 새 워커가
  아직 일하는 중인데도 **직전 메일이 즉시 다시 나와** 완료로 오인한다.
  ack 와 대기를 한 번에: `check --ack <delivery_id> --wait --types … --json`.
- ⚠️ **디스패치 capability 가 폐기되면 메시지 채널이 통째로 막힌다.**
  `dispatch_capability_invalid`(「capability is revoked」)가 나오면 `worker_done` 도 `heartbeat` 도
  거부된다(거부된 메일이 `escalation`·`status` 로 재전송돼 같은 보고가 두세 번 도착하기도 한다).
  **워커 실패가 아니다** — 프로세스는 정상으로 돈다. 완료 보고를 **파일로 받아라**: 워커에게
  「끝나면 워크트리 루트에 `DONE.md` 를 쓰라」고 지시하고 그 파일을 폴링한다.
- **터미널 핸들은 재발급된다.** `worker-start` 응답의 핸들을 나중에 다시 쓰면
  `terminal_worktree_mismatch` 가 난다. `orca terminal list --json` 에서 워크트리·제목으로 다시 찾아
  **새 핸들만** 쓴다(옛 핸들과 양쪽으로 보내지 않는다). 기존 워커를 이어 쓸 때는 `--terminal <handle>`
  과 `--worktree` 를 **함께** 준다 — `--terminal` 만 주면 워크트리가 기본값(최상위)으로 잡혀 거부된다.
- ⚠️ **Orca 런타임이 재시작되면 세션의 Run 바인딩이 다른 세션의 Run 으로 넘어갈 수 있다.**
  증상 셋: (a) `check --wait` 가 `waiter_exists` 로 거부된다(**남의 세션이 그 Run 에 waiter 를 걸어
  둔 것**) (b) 내 워커의 `worker_done` 이 안 온다 (c) 반대로 **남의 배치가 내 `check` 에 재생된다**.
  - **감지**: 태스크를 만들기 전에 `orca orchestration check --peek --json` 의 `runId` 가 내 Run 인지
    본다. `worker-show --dispatch <id>` 의 `run_id` 로도 확인된다.
  - **복구**: `orca orchestration run-use --id <내 Run>`. 단 **이미 디스패치된 워커의 `worker_done`
    은 그 dispatch 가 속한 Run 으로 간다** — 진행 중인 워커가 있으면 그 워커가 끝난 뒤에 되돌려라.
  - **끊긴 대기의 대안**: `waiter_exists` 로 막히면 터미널을 직접 읽거나 결과물(git 커밋 등)을
    폴링한다. 워커는 멀쩡히 돌고 있다.

## 4. sub-project 하나를 도는 흐름

1. **brainstorming** — 설계 결정을 사용자와 확정한다(특히 load-bearing 결정 1~2개는 반드시 질문).
2. **spec 작성** → `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 커밋.
3. **계획 작성** → `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` 커밋(태스크별 완결 코드·테스트·
   커밋 명령 포함). **계획서는 그 사이클을 도는 동안의 작업 문서다 — 사이클이 끝나 main 에 병합되면
   지운다.** 결정의 근거는 `specs/` 가, 결과는 코드와 `git log` 가 들고 있어 계획서만 남으면 순수
   부채다.
4. **태스크별 구현 → 태스크별 리뷰 → 필요 시 수정 → 재리뷰.** 워커는 Orca 터미널로 띄운다(2·3절).
5. **전체 스위트 체크포인트 → 최종 whole-branch 리뷰 → 수정 → 스모크(실 앱 + 실 DB) → main 머지,
   브랜치 삭제.**

### 계획의 가장 약한 고리는 테스트 기대값이다

**계획을 커밋하기 전에 (a) 설계 문서의 규칙·테스트 목록과 기계적으로 대조하고 (b) 픽스처의 실제
값을 열어 확인해라.** 이 대조가 착수 전에 결함을 여러 건 잡았고, 그중에는 **설계 자체의 결함**도
있었다. 픽스처를 열지 않으면 그것들이 전부 구현 중에 터진다.

### 최종 리뷰는 태스크별 리뷰가 전부 clean 이어도 반드시 한다

7태스크가 모두 Critical/Important 0건이었는데 최종 리뷰가 Critical 1건 + Important 2건을 잡은 적이
있다. 셋 다 **태스크 경계를 가로지르는** 결함이라 스코프가 좁은 게이트로는 구조적으로 볼 수 없다.
**설계 문서 안에 이미 모순의 재료가 다 있어도 태스크 단위로는 아무도 그 둘을 나란히 놓지 않는다.**

최종 리뷰 프롬프트에 이 한 줄을 넣으면 그런 결함이 바로 드러난다:

> **「이번 브랜치에서 두 번째 호출자가 생긴 기존 함수를 전부 나열하고, 양쪽 호출자 기준으로
> 그 함수의 불변식을 재유도하라.」**

### 서브에이전트·워커 프롬프트에 반드시 넣을 세 문장

**이 저장소의 지배적 결함군은 틀린 코드가 아니라 아무것도 붙잡아 두지 않는 맞는 코드다.**
한 사이클에서는 **그 사이클의 존재 이유인 계약 자체가 무테스트**였다(구현을 뒤집어도 core 스위트가
전부 통과했다). 다음 세 지시가 그것을 드러낸다.

1. **구현자에게:** 「브리프의 기대값이 실제와 어긋나면 프로덕션 코드를 기대값에 맞추지 말고, 이전
   태스크 산출물도 고치지 마라 — **단언을 정정하고 관찰한 것을 명령 출력과 함께 보고하라. 판단은
   컨트롤러가 한다.**」
2. **구현자에게, 수정 건마다:** 「그 수정이 구분력이 있는지 확인하라 — 프로덕션 변경을 되돌려
   테스트가 실패하는지 보고 복구하라. **실패하지 않으면 덮지 말고 그렇다고 보고하라.**」
   부정적 결과를 보고해도 된다는 명시적 허용이 정직한 보고를 만든다.
3. **수정 워커에게:** 「**리뷰 보고서의 제안도 검증되지 않은 주장이다** — 그대로 통과한다고 가정하지
   말고 실측한 뒤, 어긋나면 다른 방법을 쓰고 근거를 보고하라.」 이 문장이 없으면 리뷰어의 잘못된
   처방이 그대로 커밋된다.

리뷰어에게는 「품질을 봐라」가 아니라 **그 태스크의 구체적 load-bearing 리스크**를 지목해 주고,
구현자의 보고는 **미검증 주장**임을 알린다.
**브리프에는 「구분력이 있다/없다」가 아니라 진단을 요구해라** — 무엇이 어떤 값으로 관찰됐고 원인이
무엇인지까지 적게 한다. 그 원인이 수정 방향을 결정한다.

### 🔥 구분력 실증은 반드시 커밋 뒤에 한다

실증은 프로덕션 코드를 일부러 훼손했다가 `git checkout -- <path>` 로 되돌리는 절차인데,
**커밋 전에 그것을 하면 `checkout` 이 그 태스크의 구현을 통째로 HEAD 로 날린다.** 훼손분만
사라지는 것이 아니라 그 파일에 쓴 것이 전부 사라진다. 실제로 일어나 구현을 재작성해야 했다.

순서는 **구현 → 테스트 초록 → 커밋 → 실증 → 되돌리기 → `git status` clean** 이다.
덤으로 실증이 「커밋된 것」을 재는 게 되어 보고의 커밋 해시와 측정 대상이 정확히 일치한다.

⚠️ **`git checkout -- <path>` 는 아직 커밋되지 않은 신규 파일에는 통하지 않는다.** untracked 라
복구할 원본이 index 에 없고 `checkout` 은 「pathspec 이 어떤 파일과도 일치하지 않는다」로 실패한다.
그런 파일은 **편집으로 되돌려야 하고, 그래서 복구가 원본과 같은지를 따로 확인해야 한다**
(변조 전 내용을 스크래치에 복사해 두고 diff 하는 것이 확실하다).
**`git status` 의 clean 확인도 여기서는 통하지 않는다** — untracked 파일은 변조해도 `??` 로 똑같이
보인다. 브리프에 「복구하고 clean 을 확인하라」만 적으면 이 갈래가 비어 있다.

⚠️ **이중 방어를 넣으면 각 방어의 단독 구분력이 사라진다.** 각각이 단독으로 충분한 가드 둘을 함께
넣으면 요구한 테스트는 **쌍만 잠그고** 한쪽 회귀는 통과시킨다(둘 다 되돌려야 FAIL). 나중에 한쪽이
지워져도 아무도 모른다. 둘 다 두려면 **각각을 단독으로 잡는 테스트**를 요구하거나, 원리상 관찰
불가능한 쪽은 그 사실을 주석으로 남기게 하라.

### 「기존 동작을 없애는」 사이클은 착수 시점에 서술을 grep 해 목록을 만들어라

그런 사이클의 결함은 거의 전부 두 종류다 — (i) 위의 「아무것도 붙잡아 두지 않는 맞는 코드」,
(ii) **변경이 기존 서술을 거짓으로 만드는 것**(코드 주석·설계 문서의 자기모순·정본의 낡은
「알려진 한계」). 없애는 대상이 바로 그 서술들이 설명하던 동작이므로 (ii) 는 성격상 필연이다.
리뷰가 하나씩 주워 담는 것보다 착수 시점에 목록을 만들어 태스크에 배분하는 편이 싸다.

## 5. 스모크는 누가 하나

- **CLI 처럼 터미널로 끝나는 것은 워커에게 시킨다**(격리 포트·격리 DB 를 브리프에 준다).
- **브라우저 스모크도 워커에게 넘길 수 있다.** Playwright MCP 는 독립 브라우저를 띄우므로
  「확장이 붙은 Chrome 프로필이 하나뿐」이라는 제약이 없다. **2번째 클라이언트도 된다** —
  별도 브라우저 컨텍스트 + 별도 계정으로 presence·실시간 수신을 검증할 수 있다.
  **픽셀 단위 조작이 오히려 낫다** — 드래그 궤적을 코드로 설계해 「고스트 잔상 안으로 커서를 12회
  떨어뜨려 히트 0회」 같은 **수치 단언**을 만들 수 있고 사람이 손으로 흔드는 것보다 재현성이 높다.
  ⚠️ `.playwright-mcp/` 를 **저장소에 남기지 않게** 브리프에 명시해라(현재 작업 디렉터리에 생긴다).
- **예외는 확장이 하나뿐인 브라우저**다 — 그 확장으로 해야 하는 것만 메인 세션이 한다.
  ⚠️ **렌더 결함은 그 확장으로 원리적으로 계측이 안 된다**([setup.md](setup.md) 「브라우저 확장으로
  렌더 결함을 계측하려 들지 마라」 절).

### ⚠️ 브라우저 스모크는 「확인 절차」가 아니라 결함을 잡는 게이트다

태스크별 리뷰 5라운드와 최종 whole-branch 리뷰를 **모두 통과한 뒤** 스모크가 Important 급을 잡은
적이 있다. 최종 리뷰가 잡은 같은 결함군의 **더 흔한 형제**였는데, 리뷰가 코드에서 출발해 그 경로를
밟지 않았다. **화면을 실제로 써 봐야 떠오르는 동선이 있다.**

### 스모크는 「동작한다」가 아니라 「고친 것이 실제로 고쳐졌다」를 봐야 한다

**대조군을 함께 돌려라.** 좋은 예의 형태는 이렇다 — ① 고친 경로를 태워 기대한 결과가 나오는지 보고
② 결함이 나던 상태를 인위적으로 만든 뒤 다시 태워 수렴하는지 보고 ③ **대조군으로 수정을 무력화한
상태에서 같은 것을 돌려** 결함이 실제로 재현되는지 확인한다. ③이 없으면 ②의 통과가 「원래 그랬던
것」인지 「고쳐서 그런 것」인지 구별되지 않는다.

## 6. 병렬 트랙(워크트리 2개 이상)

- **트랙별 격리 DB 를 미리 만들어 준다.** 공유 `erdd_test` 를 두 트랙이 함께 쓰면 서로의 데이터를
  지운다.
- **각 워커에게 `main` 체크아웃·머지 금지를 명시한다**(같은 저장소의 다른 워크트리가 `main` 을
  잡고 있으면 git 이 거부한다). 워커는 구현+테스트+최종 리뷰까지, 병합·문서 갱신은 컨트롤러가 한다.
- **정본 문서는 어느 트랙도 건드리지 않게 한다** — 양쪽이 고치면 병합 충돌이 확정이다.
  컨트롤러가 병합 후 일괄 갱신한다.
- **마이그레이션 번호는 반드시 충돌한다**(둘 다 같은 번호를 만든다). 워커에겐 신경 쓰지 말고 각자
  격리 DB 에 적용하라고 하고, 병합 시 컨트롤러가 나중 트랙의 파일을 버리고 **병합된 스키마에서
  `drizzle-kit generate` 로 새 번호를 뽑는다**(스냅샷 손수정보다 안전하다).
- **병합 비용의 실측 형태:** 파일 충돌 십여 개 + 교차 타입/테스트 오류 수십 곳. 대부분 「두 트랙이
  같은 엔티티에 각각 새 필드를 추가」해서 생긴 기계적 충돌이라 양쪽 필드를 모두 살리면 된다.
  다만 **의미 판단이 필요한 곳이 섞인다.**
- **새 런타임 의존성이 붙은 트랙을 병합하면 `pnpm install` 을 먼저** 해야 타입이 풀린다.

### ⚠️ 트랙이 셋 이상이면 「같은 상태를 각자 바꾸는」 충돌이 난다

포트·DB 만 갈라 놓는 것으로는 부족하다. 두 트랙이 **같은 store 상태를 서로 다른 규약으로** 만든
적이 있다(주 선택을 `[0]` 으로 볼 것인가 `at(-1)` 로 볼 것인가, presence 프로토콜을 건드릴 것인가).
**기계적 충돌이 아니라 의미 충돌이라 병합기가 잡지 못한다.** 양쪽 컨트롤러가 서로의 존재는 알았지만
**어떤 상태를 건드리는지는 몰랐다** — 포트 표는 공유됐는데 **「내가 소유할 파일·상태」 목록은
공유되지 않았다.**

**트랙을 띄우기 전에:**

1. `git worktree list` 로 **다른 세션이 띄운 워크트리가 있는지 먼저 본다.** 자기 세션이 만든 것만
   있다고 가정하지 마라.
2. 있으면 그 브랜치의 `git log --oneline main..<브랜치>` 와 `docs/superpowers/plans/` 의 최신 계획을
   읽어 **소유 파일·상태가 겹치는지** 확인한다.
3. 겹치면 **먼저 끝나는 쪽을 병합하고 나중 트랙이 조정한다.** 진행도가 앞선 쪽을 먼저 병합하는 것이
   되짚는 양이 적다.
4. 각 트랙의 스펙에 **「내가 소유하는 파일·상태」**를 적어 두면 다음 트랙이 그것을 읽고 비켜 갈 수 있다.

**나중 트랙이 조정할 때는 규약 판정이 일이다.** 기계적 충돌은 거의 없다 — 컨트롤러가 규약 판정을
미리 정해 브리프에 넣었더니 워커가 물어 온 것은 하나뿐이었다.
**판정을 브리프에 미리 넣지 않으면 워커가 매번 멈춘다.**

⚠️ **병합으로 사라지는 테스트를 세어라.** 자동 병합이 main 쪽 테스트 십수 건을 지운 적이 있고
그중 하나가 어떤 계약을 덮던 **유일한 그물**이었다. 병합 워커가 세어 보고 다시 잠가야 한다.

## 커밋

- **`git add -A` / `git add .` / `git commit -a` 금지.** 남의 작업 중인 파일이 섞인다.
- **커밋할 파일을 경로로 명시한다.** 가장 안전한 형태는 **경로 지정 커밋**이다 — index 를 아예
  거치지 않는다.
  ```bash
  git commit -m "..." -- <경로1> <경로2>
  ```
- ⚠️ **`add` 와 `commit` 사이에 틈을 두지 마라.** index 는 저장소 전체가 공유하는 **단일 자원**이다.
  스테이징해 두고 다른 일을 하면 그 사이 다른 작업이 `add -A`/`commit -a` 로 커밋할 때 내 staged
  파일이 그 커밋에 통째로 딸려 들어간다. 굳이 `add` 를 쓴다면
  `git add <경로들> && git commit ...` 로 한 명령에 붙인다.
- 커밋 직전에 `git status` 로 stage 목록을 확인한다. 내가 건드리지 않은 파일이 있으면 멈추고
  사용자에게 알린다.
- `.idea/*` 와 루트 `.env` 는 커밋하지 않는다.
- **stash 는 공유 자원이다.** 워크트리들과 최상위가 stash 스택 하나를 나눠 쓴다. bare
  `git stash`/`git stash pop` 을 쓰지 마라 — 남의 것을 꺼낼 수 있다. 임시 WIP 커밋이 안전하다.

## 알려진 한계

- **서브에이전트는 한 세션에 200개까지다.** 한도에 도달하면 그 뒤로는 컨트롤러가 직접 구현+자기
  리뷰로 마쳐야 한다. 계속 쓰려면 `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` 을 올린다.
- **워커 브리프 주입은 신뢰할 수 없다.** 3절의 파일 경유가 우회이고, 그 우회는 `worker_done` 을
  잃는다(같은 절의 대응). 이것은 Orca 쪽 성질이라 이 저장소에서 고칠 수 없다.
