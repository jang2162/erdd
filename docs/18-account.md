# 계정·조직·온보딩

## 목적

계정 체계와 조직 관리를 정의한다. 초기 운영은 셀프 가입 대신 **관리자가 일회용 초대 링크를 발급해 전달하는 폐쇄형 모델**로 시작한다 — 메일 발송 인프라 없이 동작한다(링크는 화면에 뜨고 관리자가 복사해 전달한다). 개인 사용자와 팀을 하나의 조직 모델로 수용해 데이터 모델을 균일하게 유지한다.

## 사용자 시나리오

- 서비스 관리자가 관리자 페이지에서 이메일과 서비스 역할을 정해 **초대 링크**를 만들고 당사자에게 전달한다.
- 설계자가 그 링크를 열어 **이름과 비밀번호를 직접 정해** 계정을 만들고, 이메일+비밀번호로 로그인해 자동 생성된 개인 공간에서 첫 프로젝트를 만든다.
- DA가 팀 조직을 만들고, 등록된 사용자는 이메일로 찾아 멤버로 추가하며 미가입자에게는 조직 초대 링크를 발급한다.

## 기능 상세

### 인증과 계정

- 로그인: 이메일+비밀번호. 세션은 httpOnly 쿠키 기반 서버 세션.
- 사용자는 로그인 후 자신의 비밀번호를 변경할 수 있다(설정 화면). 비밀번호 분실은 **관리자가 재설정 링크를 발급**해 대응한다 — 관리자가 새 비밀번호를 정하지 않는다.
- **관리자는 남의 평문 비밀번호를 알지 못한다.** 평문 비밀번호가 존재하는 지점은 셋뿐이다: 본인이 로그인 폼에 입력할 때, 본인이 초대 수락·재설정 화면에서 정할 때, 부트스트랩 환경변수(`ADMIN_EMAIL`/`ADMIN_PASSWORD` — 초대할 사람이 아직 없는 첫 계정이라 구조적으로 필요하다). 관리자 화면에는 비밀번호 입력란이 하나도 없다.
- **일회용 링크의 성질**: 초대는 7일, 재설정은 24시간 만료이고 둘 다 한 번 쓰면 죽는다. 재발급하면 **이전 미사용 링크가 함께 만료된다** — 두 링크가 동시에 살아 있으면 안 된다. 발급 시점에 한 번만 보이며 다시 조회할 수 없다(잃으면 재발급).
- **메일 발송, 완전 개방형 셀프 가입, 소셜 로그인은 현재 비범위**([90-roadmap](90-roadmap.md) "추후 검토"). 링크는 관리자가 직접 전달한다. 그래서 로그인 화면에 "비밀번호 찾기"가 없다 — 메일이 없는 상태에서 그것을 두면 미인증 공개 엔드포인트가 계정 존재 여부 탐색 표면이 될 뿐 어차피 관리자가 링크를 전달해야 한다.

### 서비스 관리자와 관리자 페이지

User는 서비스 역할(admin/user)과 활성 여부를 가진다(→ [01-concepts](01-concepts.md)). 최초 admin 계정은 서버 부트스트랩(환경 변수 기반 시드)으로 생성한다.

관리자 페이지(admin 전용):

- 계정 목록·검색
- **계정 초대**: 이메일과 서비스 역할(admin/user)을 정해 초대 링크를 발급한다. **이 시점에는 계정이 만들어지지 않는다** — 수락자가 링크를 열어 이름과 비밀번호를 정할 때 만들어지고, **그때 개인 조직이 함께 생성된다.** 이름은 관리자가 적지 않는다. 서비스 역할은 초대 행이 들고 있어 수락자가 스스로 올릴 수 없다. 이미 가입한 이메일에는 초대를 만들 수 없다.
- **발급한 초대 목록·취소**: 관리자 초대(조직 합류 없는 초대)의 대기·만료·사용됨을 보고 취소한다. 이미 사용된 초대는 취소되지 않는다.
- **비밀번호 재설정 링크 발급**: 대상 계정의 재설정 링크를 만든다. **링크 발급만으로는 비밀번호가 바뀌지 않고 기존 세션도 그대로 살아 있다** — 사용자가 링크를 열어 새 비밀번호를 정할 때 바뀌고, **그 시점에 그 사용자의 세션이 전부 삭제된다.** 비활성 계정에는 발급하지 않는다(링크는 동작하지만 로그인이 막혀 원인이 어디에도 안 보인다 — 먼저 활성화해야 한다).
- 계정 비활성화/활성화: 비활성 계정은 로그인 불가

### 조직: 개인과 팀

Organization은 `종류(개인/팀)`를 가진다.

- **개인 조직**: 계정 생성 시 자동 생성. UI에서 "개인 공간"으로 표시. 삭제·멤버 추가·소유권 이전 불가. 무료 티어 = 개인 조직의 플랜(제한 집행은 Phase 4 과금 설계에서).
- **팀 조직**: 사용자가 직접 생성(생성자가 Owner). Phase 1에서는 플랜 제한 없이 동작한다.

### 조직 멤버 관리

- Org Owner/Admin이 **등록된 사용자를 이메일로 찾아 멤버로 직접 추가**하고 역할(Admin/Member)을 지정한다.
- **미가입자는 조직 초대 링크로 받는다.** Org Owner/Admin이 이메일과 역할(Admin/Member)을 정해 링크를 발급하면, 수락자가 계정을 만들면서 그 조직의 멤버가 된다(개인 조직도 함께 생긴다). **계정 생성·개인 조직·조직 합류·초대 소비는 한 트랜잭션이다** — 중간에 끊겨 "계정은 생겼는데 조직에 못 들어간" 상태가 되면 초대는 이미 소비돼 복구 경로가 없다. 조직 초대로는 서비스 역할을 올릴 수 없고(항상 user), Owner도 줄 수 없다. 이미 가입한 이메일에는 초대를 만들 수 없다 — 멤버 추가를 쓴다. 개인 조직에는 초대를 만들 수 없다.
- 마지막 Owner는 제거·강등할 수 없다. Owner 역할 부여/회수는 Owner만 가능하다.
- 프로젝트 참여는 조직 멤버 중에서 ProjectMember(Admin/Editor/Viewer)로 추가한다([01-concepts](01-concepts.md)의 권한 모델).

### 온보딩

- 로그인 → 개인 공간 → 첫 프로젝트 생성 유도(이름 + 대상 DB 방언 선택).
- AccessToken(개인 액세스 토큰) 발급 UI는 CLI와 함께 Phase 4(→ [16-cli](16-cli.md)).

## 단계별 범위

- **Phase 1**: 위 기능 전체 — 로그인/비밀번호 변경, 관리자 페이지(초대 링크 발급·재설정 링크 발급·비활성화), 개인·팀 조직, 멤버 직접 추가, 조직 초대 링크, 온보딩.
- **Phase 4**: 무료 티어 제한 집행(과금 설계와 함께).
- **추후 검토**: **메일 발송**(초대·재설정 링크를 메일로 보내는 것, 그와 함께 로그인 화면의 "비밀번호 찾기"), 완전 개방형 셀프 가입(도메인 허용목록·가입 요청 승인 큐), 소셜 로그인. **초대와 비밀번호 재설정 자체는 링크로 해소됐고 남은 것은 발송 한 겹이다** — 지금의 토큰·화면을 그대로 두고 얹으면 된다.
