# 캔버스 다중 선택 + 클립보드 + 단축키 (트랙 C) — 설계

**작성일:** 2026-08-10 / **base:** `main` (`2b0bebc`) / **마이그레이션:** 없음 / **서버 변경:** 없음

> 이 사이클은 **트랙 A+B**(`2026-08-10-physical-first-naming-design.md`)와 **병렬**로 진행한다.
> 겹치는 파일은 `apps/web/src/editor/edit-panel.tsx` 하나다 — 이 트랙은 컬럼 행의 **선택 상태·
> 하이라이트·스크롤**을, 트랙 A+B는 컬럼 행의 **입력 필드 순서와 라벨**을 건드린다.

## 1. 목적과 범위

지금 캔버스에서 할 수 있는 것은 **테이블 하나를 고르는 것**뿐이다. 컬럼은 선택 대상이 아니고,
복사·붙여넣기가 없어 비슷한 테이블을 여러 개 만들 때 매번 컬럼을 손으로 다시 친다. 이 사이클은
선택 모델을 넓히고 그 위에 클립보드와 단축키를 얹는다.

**범위 안**
- C-1 테이블 다중 선택 + 컬럼 다중 선택
- C-2 캔버스에서 컬럼을 클릭하면 사이드바가 그 컬럼으로 스크롤·하이라이트
- C-3 복사/잘라내기/붙여넣기 (테이블 단위 · 컬럼 단위, 시스템 클립보드 JSON)
- C-4 단축키 — Cmd/Ctrl+C·X·V, Delete/Backspace

**범위 밖**
- **실시간 presence 프로토콜 변경** (D-C5) — 컬럼 선택은 로컬 전용
- 관계선 복사 (D-C3)
- 그룹·메모의 복사·붙여넣기 (테이블·컬럼만)
- 드래그 앤 드롭으로 컬럼을 다른 테이블에 옮기기

## 2. 확정된 결정 (사용자 확정)

### D-C1. 컬럼 선택은 **테이블 선택에 종속**된다

컬럼은 항상 한 테이블 안에 있다. 여러 테이블에 걸친 컬럼 선택은 만들지 않는다 — 복사 단위가
모호해지고("두 테이블의 컬럼을 어디에 붙여넣나"), 사이드바가 한 테이블만 보여주는 현재 구조와
어긋난다.

### D-C2. 테이블도 다중 선택한다

⚠️ **원안의 전제가 틀렸다** (구현 중 발견, 2026-08-10). 원안은 "React Flow가 드래그 박스·Shift 클릭
다중 선택을 이미 지원하므로 비용의 대부분은 store의 단일 선택을 배열로 바꾸는 일"이었다. 실제로는
**React Flow의 선택이 별개의 진실 원본**이라 store로 흐르는 동기화 코드가 따로 필요하다 —
`onSelectionChange` 배선이 없으면 드래그 박스·Shift 선택은 React Flow 내부 상태만 바꾼다.

**단일 진실 원본은 store다.** React Flow의 선택은 **입력 이벤트**로만 쓰고, 무엇이 선택돼 보이는지는
언제나 store에서 나온다. 그래서 필요한 것은 넷이다:

1. `buildNodes`가 `data.selected`뿐 아니라 **노드 최상위의 `selected`**도 같은 값으로 채운다 —
   `setNodes(derived)`가 React Flow의 내부 플래그를 덮어써도 값이 같아 화면이 튀지 않는다.
   경쟁을 없애는 것이 아니라 양쪽 값을 같게 만들어 무해하게 만드는 것이다.
2. `onSelectionChange` → `selectTables`. 테이블 노드만 거른다(ghost·group·note 제외). 현재 선택과
   같은 집합이면 **호출하지 않는다** — 같은 값으로 `set`을 반복하면 배열 참조가 매번 새로 생겨
   리렌더 루프가 난다.
3. `onNodeClick`의 Cmd/Ctrl+클릭 → `toggleTable`.
4. 드래그 박스는 **React Flow 기본(Shift+드래그)**을 쓴다. `selectionOnDrag`를 켜면 좌클릭 드래그가
   선택이 되면서 팬이 막힌다.

⚠️ **이 결함이 늦게 드러난 이유가 더 중요하다.** 다중 선택 테스트가 `selectTables(['t1','t2'])`를
**직접 호출**해 패널·잘라내기·삭제를 검증했고, 그 사이 **사용자 경로가 없다는 사실은 아무도 보지
않았다.** 통과하는 테스트가 도달 불가능한 코드를 지키고 있었던 것이다. 그래서 이 배선의 테스트는
반드시 **사용자 조작에서 출발**해야 한다 — 캔버스 클릭·`onSelectionChange`가 store를 바꾸는지.

### D-C3. 복사는 **인덱스까지, 관계는 제외**

인덱스는 테이블 내부 구조라 그대로 따라간다. 관계는 상대 테이블이 있어야 성립하므로, FK 컬럼은
일반 컬럼으로 남기고 선을 만들지 않는다. "양쪽 다 복사된 경우에만 재연결"은 검토했으나 배제했다 —
규칙과 테스트가 크게 늘고, 붙여넣기 결과를 사용자가 예측하기 어려워진다.

### D-C4. 클립보드는 **시스템 클립보드 JSON**이다 (다른 프로젝트·탭까지)

앱 내부 메모리 클립보드는 같은 탭 안에서만 산다. 다른 프로젝트로 테이블을 옮기는 것이 이 기능의
주 용도이므로 시스템 클립보드를 쓴다.

**참조 처리:** 도메인·용어는 **이름으로 재연결**하고, 붙여넣는 프로젝트에 같은 이름이 없으면
`domainId: null` + 복사본의 `type` 문자열을 유지한다.

**이름 충돌:** 자동 개명한다. 논리명은 `주문` → `주문_사본` → `주문_사본2`, 물리명은 `ORD` →
`ORD_COPY` → `ORD_COPY2`.

### D-C5. presence 프로토콜은 건드리지 않는다

`PeerSelection`은 `{ kind: 'table', id }` 단일 값이다(`realtime-protocol.ts`). 다중·컬럼 선택을 실으려면
core 프로토콜 + 서버 + 클라 양쪽이 움직이고, 그것은 이 사이클보다 큰 주제다. **다중 선택 시
첫 번째 테이블만** 발신한다 — 남에게 보이는 하이라이트는 지금과 똑같이 동작한다.

## 3. 의미 모델

### 3.1 `selectedTableId`를 `selectedTableIds`로 **교체**한다 (병기하지 않는다)

⚠️ **이것이 이 사이클의 load-bearing 결정이다.** 기존 `selectedTableId: string | null`을 남긴 채
`selectedTableIds: string[]`를 추가하면 **같은 사실에 두 개의 진실 원본이 생긴다.** 이 저장소는 이미
그 형태로 Critical을 한 번 맞았다 — `store.seq`에 두 가지 의미가 생겨 남의 op가 영구 유실된
사고다(HANDOFF 3.6 "store.seq에는 의미가 하나여야 한다").

그래서 **배열 하나로 교체하고**, 단일 선택을 요구하는 기존 소비자는 `selectedTableIds[0] ?? null`로
유도한다. 고쳐야 할 소비자는 6곳이다:

| 파일 | 쓰임 | 교체 후 |
|---|---|---|
| `editor/edit-panel.tsx:49` | 선택된 테이블의 편집 폼 | 1개면 폼, 2개 이상이면 「N개 선택됨」 |
| `editor/toolbar.tsx:19,53,98` | 삭제 버튼 활성·대상 | 선택 전체 삭제 |
| `editor/table-tree.tsx:15,75,87` | 트리 항목 하이라이트 | `includes(t.id)` |
| `editor/canvas.tsx:33` | 노드 `selected` 표시 | `includes(id)` |
| `editor/use-realtime.ts:38,124` | presence 발신 | `[0]`만 (D-C5) |
| `editor/store.ts` | 상태·액션 | 아래 3.2 |

### 3.2 선택 상태의 정의

```
selectedTableIds: string[]      // 순서 = 선택한 순서. [0]이 presence·사이드바의 기준
selectedColumnIds: string[]     // selectedTableIds.length === 1 일 때만 비어 있지 않을 수 있다
```

**불변식:** `selectedTableIds.length !== 1`이면 `selectedColumnIds`는 반드시 빈 배열이다. 테이블 선택이
바뀌면 컬럼 선택을 비운다. 이 불변식을 store의 액션 안에서 지키고, 컴포넌트가 각자 판단하지 않게 한다.

기존 `CLEARED_SELECTION`(테이블/관계/메모/그룹 상호배타)은 그대로 유지하고 두 배열을 그 안에 넣는다.
`resync`의 `keep` 패턴(`store.ts:95`)도 배열용으로 확장한다 — **원격 삭제된 컬럼 id가 선택에 남으면
사이드바가 없는 컬럼을 가리킨다.**

### 3.3 클립보드 형식

```jsonc
{
  "__erdd": 1,          // 이 앱이 쓴 것인지 판별하는 표식
  "v": 1,               // 형식 버전
  "kind": "tables",     // 또는 "columns"
  "items": [ /* 아래 3.4 */ ]
}
```

- 붙여넣기는 `__erdd !== 1`이면 **조용히 무시**한다. 사용자가 다른 앱에서 복사한 텍스트를 캔버스에
  붙여넣는 것은 정상적인 오작동이므로 오류를 띄우지 않는다
- `v`가 모르는 값이면 무시한다. 형식이 바뀔 때 옛 클립보드가 조용히 깨진 결과를 만들지 않게 한다

### 3.4 무엇을 싣는가 — **id는 싣지 않는다**

붙여넣기는 항상 `newId()`로 새 엔티티를 만든다. 원본 id를 실어 봐야 다른 프로젝트에서는 무의미하고,
같은 프로젝트에서는 충돌한다.

**도메인 참조는 id가 아니라 이름으로 싣는다** — `domainName: string | null`. 붙여넣을 때 그 이름의
도메인을 찾아 연결하고, 없으면 `domainId: null`로 두고 복사본의 `type` 문자열을 그대로 쓴다.

같은 이유로 **커스텀 항목 값**(`custom`)은 **키가 `customField` id**이므로 그대로 실으면 다른
프로젝트에서 dangling이 된다. 모델은 dangling 키에 관대하지만(HANDOFF 1절 "dangling 키 관대"),
붙여넣기가 쓰레기를 만들 이유는 없다 — **커스텀 항목 값도 필드 이름으로 싣고 이름으로 재연결한다.**
같은 규칙 하나가 도메인과 커스텀 항목 양쪽을 덮는다.

### 3.5 개명 규칙

붙여넣는 프로젝트에서 이미 쓰이는 이름이면 접미사를 붙여 비켜 간다.

- 논리명: `X` → `X_사본` → `X_사본2` → `X_사본3` …
- 물리명: `X` → `X_COPY` → `X_COPY2` …

**검사 범위:** 테이블 붙여넣기는 프로젝트 전체 테이블, 컬럼 붙여넣기는 **대상 테이블 안**에서만
본다(컬럼 물리명 중복 경고가 테이블 단위이므로 그 단위와 맞춘다).

⚠️ 물리명 길이 제한(`maxLengthBytes`)에 걸릴 수 있다. 접미사를 붙여 넘치면 `too-long` 경고가
잡는다 — 붙여넣기가 자르지 않는다. 자르면 이름이 조용히 뭉개지고, 경고는 이미 있는 표면이다.

### 3.6 잘라내기는 **단일 mutation**이다

복사(클립보드 쓰기)는 모델을 바꾸지 않고, 삭제만 mutation이다. 여러 테이블·컬럼을 지우는 것도
**한 producer 안에서** 처리해 Revision 1건 · undo 1회로 되돌아가게 한다.

### 3.7 단축키가 언제 동작하지 않는가

`document`에 리스너를 걸되 다음이면 **아무것도 하지 않고 기본 동작에 넘긴다**:

- `event.target`이 `input` / `textarea` / `contenteditable`
- 다이얼로그가 열려 있을 때 (편집 다이얼로그 안의 복사·붙여넣기는 브라우저 기본 동작이어야 한다)
- `canEdit`가 false면 X·V·Delete는 무시하고 C만 허용

**현재 `deleteKeyCode='Backspace'`(`canvas.tsx:133`)와의 관계:** React Flow의 자체 삭제 처리를 끄고
(`deleteKeyCode={null}`) 이 사이클의 단축키 핸들러가 Delete·Backspace를 모두 받는다. 두 경로가
공존하면 컬럼 선택 상태에서 어느 쪽이 이기는지가 렌더 순서에 달리게 된다.

### 3.8 붙여넣기는 `paste` 이벤트로 받는다

`navigator.clipboard.readText()`는 브라우저에 따라 권한 프롬프트를 띄운다. Cmd/Ctrl+V를 누른 사용자에게
권한 창이 뜨는 것은 받아들일 수 없으므로 **`paste` 이벤트의 `clipboardData`**를 읽는다. 쓰기
(`writeText`)는 사용자 제스처 안에서 일어나므로 그대로 쓴다.

## 4. core 변경

**없다.** 클립보드 직렬화는 `apps/web`의 관심사다 — core는 IO·런타임 의존성 free이고(HANDOFF 3.5),
`navigator.clipboard`·`ClipboardEvent`에 닿는 코드는 core에 들어갈 수 없다.

다만 **순수 변환 함수는 core에 두지 않되 순수하게 유지한다**(5.2) — 테스트가 DOM 없이 돈다.

### 5.2 `clipboard.ts` — 순수 함수 경계

```
serializeTables(model, tableIds): ClipboardPayload
serializeColumns(model, columnIds): ClipboardPayload
parseClipboard(text): ClipboardPayload | null          // __erdd·v 검사 포함
```

`clipboard-edits.ts`는 `pasteTables(model, payload, position)` / `pasteColumns(model, payload, tableId)`로
**모델 → 모델** producer를 낸다. 재연결·개명이 여기서 일어난다. id 발급은 producer 진입 **전에**
확정해 넘긴다 — `serializeMutation`이 producer를 마이크로태스크로 지연 실행하므로 producer 안에서
`newId()`를 부르면 재실행 시 다른 id가 나온다(HANDOFF 3.4 "이벤트 값은 producer 진입 전에 캡처",
N:M 사이클의 `planJunction`이 같은 이유로 id·좌표를 미리 계산한다).

### 5.3 컬럼 클릭 → 사이드바 포커싱

`table-node.tsx`의 컬럼 행에 클릭 핸들러를 단다. 수식 키 조합:

| 입력 | 동작 |
|---|---|
| 클릭 | 그 테이블 선택 + 그 컬럼만 선택 |
| Cmd/Ctrl + 클릭 | 컬럼 선택 토글 |
| Shift + 클릭 | 마지막 선택 컬럼부터 범위 선택 |
| 테이블 헤더 클릭 | 테이블만 선택 (컬럼 선택 해제) |

편집 패널은 `selectedColumnIds`가 바뀔 때 `[0]`에 해당하는 행으로 `scrollIntoView({ block: 'nearest' })`
한다. **`nearest`인 이유**: 이미 보이는 컬럼을 클릭했을 때 패널이 튀지 않아야 한다.

### 5.4 다중 선택 시 편집 패널

테이블이 2개 이상 선택되면 폼 대신 「N개 선택됨」과 함께 **선택 전체에 대한 동작**(삭제·복사)만
보여준다. 폼을 그리면 어느 테이블의 값인지 모호해진다.

## 6. 테스트 전략

### 6.1 순수 함수 (`clipboard.test.ts` · `clipboard-edits.test.ts`)

- 직렬화 왕복 — 테이블·컬럼·인덱스가 보존되고 **관계는 실리지 않는지**
- `parseClipboard` — `__erdd` 없음 / `v` 불일치 / JSON 아님 → 전부 `null`
- 도메인 재연결 — 같은 이름 있으면 연결, 없으면 `domainId: null` + `type` 유지
- 커스텀 항목 재연결 — 같은 규칙
- 개명 — 1차 `_사본`, 2차 `_사본2`, 물리명 `_COPY`. 충돌이 없으면 **개명하지 않는지**
- 컬럼 붙여넣기의 개명 범위가 **대상 테이블 안**인지 (다른 테이블의 동명 컬럼은 무관)

### 6.2 store (`store.test.ts`)

- **불변식**: 테이블을 2개 선택하면 `selectedColumnIds`가 비는지
- 테이블 선택이 바뀌면 컬럼 선택이 비는지
- `resync`에서 원격 삭제된 컬럼·테이블 id가 선택에서 빠지는지

### 6.3 컴포넌트

- `table-node.test.tsx` — 클릭/Cmd+클릭/Shift+클릭의 선택 결과
- `edit-panel.test.tsx` — 선택된 컬럼 행에 하이라이트가 붙는지, 다중 테이블 선택 시 「N개 선택됨」
- `canvas.test.tsx` — `paste` 이벤트로 붙여넣기가 되는지, `__erdd` 아닌 텍스트는 무시되는지
- 단축키 — 입력란에 포커스가 있으면 **동작하지 않는지**(이게 회귀하기 가장 쉽다)

### 6.4 구분력 (필수)

- **불변식 테스트가 불변식을 잡는지** — store 액션에서 컬럼 비우기를 지웠을 때 실패해야 한다
- **입력란 가드** — 가드를 지웠을 때 실패해야 한다. `document`에 리스너를 걸면 텍스트를 치는 중에
  Delete가 테이블을 지우는 사고가 나는데, 이 테스트가 유일한 방어선이다
- **개명 테스트가 개명을 잡는지** — 개명 로직을 항등으로 바꾸면 실패해야 한다. "붙여넣으면 테이블이
  2개가 된다"만 단언하면 개명 여부와 무관하게 통과한다
- **관계 제외** — 관계를 싣도록 바꾸면 실패해야 한다

### 6.5 브라우저 스모크

1. 컬럼 클릭 → 사이드바가 그 컬럼으로 스크롤·하이라이트되는지
2. Cmd/Ctrl+클릭·Shift+클릭으로 컬럼 여러 개 선택 → Cmd+C → 다른 테이블 선택 → Cmd+V
3. 테이블 드래그 박스로 여러 개 선택 → Cmd+X → Cmd+V → **undo 1회로** 전부 복구되는지 (3.6)
4. **다른 프로젝트 탭**에 붙여넣기 → 도메인이 이름으로 재연결되는지, 없는 도메인은 「없음」인지
5. 같은 프로젝트에 두 번 붙여넣기 → `_사본`, `_사본2`
6. 입력란에 텍스트를 치는 중 Delete·Cmd+C가 **테이블을 건드리지 않는지**
7. **대조군**: 다른 앱에서 복사한 일반 텍스트를 캔버스에 붙여넣기 → 아무 일도 없어야 한다

## 7. 알려진 한계 (이월 후보)

- **컬럼 선택은 남에게 보이지 않는다**(D-C5). presence는 테이블 단위 그대로다
- **관계가 복사되지 않는다**(D-C3). 테이블 묶음을 옮기면 선을 다시 그어야 한다
- 그룹·메모는 복사 대상이 아니다
- 붙여넣은 테이블의 **위치**는 원본 좌표 + 고정 오프셋이다. 겹치면 사용자가 옮긴다
- 개명이 물리명 길이 제한을 넘길 수 있다(3.5). `too-long` 경고가 잡지만 자동으로 줄이지는 않는다
