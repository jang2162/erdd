# 테이블 논리명 형식 템플릿 + 접기 규칙 변경 — 설계

**작성:** 2026-08-18 / **상태:** 사용자 확정 / **마이그레이션:** 없음(jsonb) /
**core 변경:** 엔진 형제 함수 + 접기 규칙 + 산출물 6자리 · **server:** 확인만 · **CLI:** 옵셔널 키 ·
**web:** 설정 입력란 + 편집 패널 미리보기

---

## 1. 목적과 범위

**테이블 논리명도 「접두 + 입력한 부분」으로 조합한다.** 직전 사이클이 물리명에 넣은 것을 논리명으로
넓히는 것이고, 원래 요청("논리/물리 둘다")의 나머지 절반이다. 함께 **접기 규칙의 경계 하나를 고친다** —
`TB_{그룹별칭}_LOG` 에서 별칭이 비면 `_LOG` 가 통째로 사라져 `TB_` 가 되던 것을 `TB_LOG` 로 만든다.

두 항목을 한 사이클에 묶는 이유: **접기 규칙은 논리명 템플릿이 재사용할 바로 그 엔진**이다. 뒤에 고치면
논리명 케이스를 두 번 쓰게 된다.

**범위 안**

| 대상 | 하는 일 |
|---|---|
| `packages/core/src/name-template.ts` | 접기 규칙 교체 + `composeTableLogicalName` 추가 |
| `packages/core/src/naming.ts` | `NamingRules.tableLogicalTemplate` + 두 스키마 |
| `packages/core/src/ddl.ts` | 코멘트 2자리 + `warningLabel` 폴백 |
| `packages/core/src/dbml.ts` | note 의 논리명 |
| `packages/core/src/excel-sheets.ts` | 논리명 열 2자리 |
| `apps/server/src/routers/project.ts` | 확인만 — 이미 `NamingRulesSchema.parse` 를 태운다 |
| `packages/cli/src/config.ts` | 옵셔널 키 |
| `apps/web` 설정 · 편집 패널 | 두 번째 입력란 · 논리명 미리보기 |

**범위 밖 (건드리지 않는다)**

- **컬럼 논리명 템플릿** — 요청이 「테이블명」이다(물리명 사이클과 같은 경계).
- **역설계 역분해** — 다음 사이클. SQL 코멘트에 메타정보를 실어 왕복을 닫는 안을 따로 검토한다(6절).
- **검사(경고) 배선** — 논리명에는 중복·길이·예약어 검사가 없다. D1 이 근거다.
- **CLI 파일·클립보드·사이드바·캔버스** — 부분을 그대로 쓴다(D3).

## 2. 확정된 결정 (사용자 확정)

### D1. 논리명 조합은 산출물 전용이다 — 사전·검사·재생성은 부분을 본다

그룹 `회원관리`, 테이블 논리명 `주문`, 템플릿 `{그룹명}_{논리명}` 일 때:

| 경로 | 보는 이름 |
|---|---|
| 용어 사전 완전일치(`generatePhysicalName` 1단계) | **주문** |
| 미등록 단어 검사 · 논리 구분자 경고 | **주문** |
| `↻` 물리명 재생성 | **주문** → `ORD` |
| DDL 코멘트 · DBML note · Excel 논리명 열 · 미리보기 | **회원관리_주문** |
| 사이드바 · 캔버스 · 편집 입력란 | **주문** |

**근거:** 조합 이름으로 사전을 찾게 하면 사용자가 사전에 `회원관리_주문` 을 등록해야 하고, 재생성이
그룹 약어를 물리명에 넣어 **물리명 템플릿과 이중 적용**된다(`TB_{그룹별칭}_` + `MBR_MGT_ORD` →
`TB_MBR_MBR_MGT_ORD`). 물리명 사이클이 용어 검사만 부분 기준으로 남긴 것과 같은 형태이고, 논리명은
용어 완전일치의 **입력 자체**라 그 판단이 더 넓게 번진다.

⚠️ 그래서 **`warnings.ts` 는 이 사이클에서 한 줄도 안 바뀐다.** 논리명에는 조합 기준이라야 의미가 있는
검사(중복·길이 30바이트·예약어)가 없다 — 그것들은 전부 물리명 쪽이다.

### D2. 접기 규칙 — 빈 변수는 인접한 **밑줄만** 지운다

> **빈 변수는 자기 자신과 바로 뒤 리터럴 선두의 밑줄들을 지운다. 뒤에 리터럴이 없으면 바로 앞
> 리터럴 말미의 밑줄들을 지운다. 변수 값은 절대 건드리지 않는다.**

지우는 단위가 「리터럴 토큰 하나」에서 「그 리터럴 선두/말미의 밑줄」로 좁아진다.

| 형식 | 상황 | 지금 | 바뀐 뒤 |
|---|---|---|---|
| `TB_{그룹별칭}_LOG` | 그룹 없음 | `TB_` ⚠️ | **`TB_LOG`** |
| `{그룹별칭}_LOG_{물리명}` | 그룹 없음 | `ORD` ⚠️ | **`LOG_ORD`** |
| `TB_{그룹별칭}_{물리명}` | 그룹 없음 | `TB_ORD` | `TB_ORD` |
| `{그룹별칭}_{물리명}` | 그룹 없음 | `ORD` | `ORD` |
| `{그룹별칭}_{물리명}` | 물리명 없음 | `MBR` | `MBR` |
| `TB_{A}_{B}_{물리명}` | A·B 둘 다 빔 | `TB_ORD` | `TB_ORD` |
| `{그룹별칭}_{물리명}` | 둘 다 빔 | `` | `` |
| `TB_{물리명}` | 물리명이 `A__B` | `TB_A__B` | `TB_A__B` |

**기존 6형의 결과가 하나도 안 바뀐다.** 바뀌는 것은 「변수 뒤 리터럴이 구분자 하나가 아닌」 두
경우뿐이고, 그쪽이 지금 잘못 나오던 자리다.

⚠️ **그래도 동작 변경이다.** 이미 `TB_{그룹별칭}_LOG` 같은 템플릿을 쓰는 프로젝트가 있으면 결과가
`TB_` 에서 `TB_LOG` 로 달라진다. 문서에 적는다.

**구분 기호는 밑줄 `_` 하나로 본다.** 이 프로젝트의 물리명·논리명 구분자가 둘 다 `'_' | ''` 라
일관되고, 규칙이 가장 좁아 예측 가능하다. 대가는 하이픈을 쓴 템플릿(`TB_{그룹별칭}-LOG`)이 별칭이 빌 때
`TB_-LOG` 가 되는 것인데, 하이픈은 인용 없이는 SQL 식별자로 못 써서 애초에 쓰일 자리가 아니다.
⚠️ **「글자·숫자가 아닌 문자」로 넓히지 마라** — 논리명 템플릿의 리터럴은 한글이고(`{그룹명}_주문건`),
ASCII 기준 판정을 쓰면 한글까지 먹는다.

### D3. 화면은 부분을 유지한다

사이드바 트리·캔버스 노드·편집 입력란은 `주문` 그대로다. 편집 패널이 논리명 입력란 아래에
`→ 회원관리_주문` 미리보기 한 줄을 붙인다(물리명과 같은 모양, 같은 자리).

**근거:** 편집하는 값과 트리가 어긋나면 사용자가 어느 것을 고쳐야 할지 모른다. 물리명 사이클 D3 이
정한 경계를 그대로 따른다.

### D4. 엔진은 형제 함수로 추가한다

```ts
export function composeTablePhysicalName(table, model, rules): string   // 기존
export function composeTableLogicalName(table, model, rules): string    // 신설
```

공통 몸통을 private `compose(template, table, model)` 로 뽑고 둘이 각자 템플릿만 골라 넘긴다.
**기존 호출처 12곳이 하나도 안 바뀐다.**

`composeTableName(table, model, rules, which)` 통합안은 12곳을 전부 고치면서 얻는 것이 없고,
`composeName(template, …)` 만 노출하는 안은 소비처가 매번 템플릿을 고르게 되어 「소비처는 템플릿을
몰라도 된다」는 계약(물리명 설계 3.1)이 깨진다.

**변수는 물리명과 같은 다섯을 그대로 쓴다** — `{그룹별칭}` `{그룹명}` `{물리명}` `{논리명}`
`{커스텀:항목이름}`. 값은 **항상 저장된 부분**(`table.logicalName`·`table.physicalName`)이라 논리
템플릿이 `{물리명}` 을 참조해도 조합 결과를 다시 참조하지 않는다 — **재귀가 원리적으로 불가능하다.**

`NamingRules.tableLogicalTemplate: string`(기본 `''`). 비면 `table.logicalName` 을 그대로 돌려준다 —
물리명과 같은 계약이라 소비처는 템플릿 유무를 모른다.

### D5. 코멘트 생략 판정은 조합끼리 비교한다

`commentText(<조합 논리명>, <조합 물리명>, comment)`.

**근거:** 직전 사이클이 물리명 쪽을 조합으로 바꿔 잠갔다(M-1). 한쪽만 조합이면 판정이 엉뚱하게 갈린다.
갈리는 입력이 실제로 있다 — 그룹명 `SALES`, 논리명 = 물리명 = `ORD`, 논리 템플릿 `{그룹명}_{논리명}`,
물리 템플릿 `{그룹명}_{물리명}`:

| 비교 방식 | 결과 |
|---|---|
| 조합 ↔ 조합 (D5) | `SALES_ORD` == `SALES_ORD` → **생략** |
| 부분 논리명 ↔ 조합 물리명 (D5 안 하면) | `ORD` != `SALES_ORD` → 코멘트가 나간다 |

**생략이 맞다.** 최종 산출물에서 두 이름이 같은데 코멘트로 한 번 더 적는 것은 잡음이다. 이 입력이
그대로 테스트 케이스가 된다(§4).

## 3. 구조

### 3.1 접기 알고리즘

토큰 배열 위에서 돈다(정규식 후처리로 흉내내지 않는다 — 변수 값 안의 연속 밑줄까지 접힌다).
**조각마다 「리터럴에서 왔는가」를 함께 들고 다녀야 한다** — 말미 밑줄을 지울 때 변수 값은 건드리면
안 되기 때문이다.

```
for 각 토큰:
  리터럴이면        → 조각으로 push (lit=true)
  변수이고 값이 있으면 → 조각으로 push (lit=false)
  변수이고 값이 비면:
    뒤 토큰이 리터럴이면 → 그 리터럴의 선두 밑줄을 지워 push 하고 그 토큰을 건너뛴다
    아니면              → 뒤에서부터 조각을 훑는다:
                           빈 조각이면 버리고 계속
                           변수 조각이면 멈춘다(값은 안 건드린다)
                           리터럴 조각이면 말미 밑줄을 지우고 멈춘다(비면 버린다)
```

⚠️ **뒤에서부터 훑는 것이 급소다.** 단순히 「직전 조각 하나」만 보면 `A_{X}_{Y}` 에서 X·Y 가 둘 다 빌
때 X 가 남긴 빈 조각에 막혀 `A_` 가 나온다. 빈 조각을 건너뛰어야 `A` 가 된다.

### 3.2 배선 6자리 (논리명)

| 파일:행 | 자리 |
|---|---|
| `ddl.ts:111` | mysql 인라인 코멘트 — `commentText(<조합 논리명>, <조합 물리명>, …)` |
| `ddl.ts:199` | 그 외 방언 `COMMENT ON TABLE` — 같은 형태 |
| `ddl.ts:135` | `warningLabel` 폴백 — 조합 물리명이 비면 **조합 논리명**으로 떨어진다 |
| `dbml.ts:130` | `buildDbmlNote(<조합 논리명>, <조합 물리명>, …)` |
| `excel-sheets.ts:127` | 테이블 목록 시트의 논리명 열 |
| `excel-sheets.ts:138` | 테이블정의서 시트의 「테이블 논리명」 열 |

⚠️ **`excel-sheets.ts:156-166` 은 손대지 마라** — 단어사전·용어사전 시트의 `logicalName` 이고
`Word`·`Term` 이지 `Table` 이 아니다.

⚠️ **정렬은 안 바뀐다.** Excel 은 `그룹명 → 조합 물리명` 순, DDL 은 조합 물리명 순이다. 논리명은
정렬 키가 아니다.

`generateDdl`·`ddlWarnings`·`generateDbml`·`buildExcelSheets` 는 **이미 `rules` 를 필수로 받는다**
(직전 사이클). 새로 뚫을 인자가 없다.

### 3.3 조합 결과가 빌 때

논리명 조합이 `''` 가 되면(예: `{그룹명}_{논리명}` 에서 둘 다 빔) `commentText` 의 첫 인자가 빈
문자열이라 논리명을 코멘트에 안 넣는다 — 설명만 나가거나 코멘트 자체가 생략된다. Excel 논리명 열은
빈 칸이다. **`required-empty` 경고는 부분 기준이라 그대로 뜬다**(물리명과 같은 조합 — 내보내기를
막지는 않되 채우라고 알린다).

⚠️ **논리명이 비어도 DDL 에서 테이블을 제외하지 않는다.** 제외 판정(`hasEmptyPhysicalName`)은
물리명만 본다 — 식별자를 만들 수 없는 것은 물리명이지 논리명이 아니다. 이 사이클이 바꾸지 않는다.

### 3.4 UI

**프로젝트 설정** — 「테이블 논리명 형식」 입력란을 「테이블 물리명 형식」 아래에 같은 모양으로 둔다.
도움말의 변수 목록도 같다. 미리보기도 같은 방식(현재 모델의 첫 테이블, 없으면 가상 예시).

**편집 패널** — 미리보기 두 줄. 각 템플릿이 비면 그 줄을 렌더하지 않는다(둘 다 비면 두 줄 다 없다).

⚠️ **현재 배치를 먼저 보라.** 물리명 미리보기는 물리명 칸 바로 아래가 아니라 **`NamePair` 전체
아래**에 있다(`NamePair` 가 물리명·논리명 두 칸을 함께 렌더하기 때문이다). 실제 화면은 이렇다:

```
테이블 물리명 *
[ ORD                    ↓ ]
미등록 [+ ORD]
논리명 *
[ 주문                    ↑ ]
미등록 [+ 주문]
→ TB_MBR_ORD              ← 물리명 미리보기(NamePair 바깥)
소속 그룹
```

미리보기가 둘이 되면 **어느 줄이 어느 이름인지 구분되지 않는다.** 라벨을 붙여 나란히 둔다:

```
물리 → TB_MBR_ORD
논리 → 회원관리_주문
```

⚠️ **`NamePair` 에 슬롯 prop 을 뚫지 마라.** 칸 바로 아래에 붙이려면 그 방법뿐인데, `NamePair` 는
컬럼과 공유하는 컴포넌트이고 컬럼에는 템플릿이 없다 — 직전 사이클이 정확히 그 이유로 미리보기를
바깥에 뒀다. **라벨 두 글자가 공유 컴포넌트에 prop 을 하나 더 얹는 것보다 싸다.**

⚠️ **물리명 미리보기의 기존 문구가 바뀐다**(`→ TB_MBR_ORD` → `물리 → TB_MBR_ORD`). 그것을 단언하는
기존 테스트(`edit-panel.test.tsx` 의 「템플릿이 있으면 조합 결과를 보여 준다」 등 3건)가 함께 바뀐다.

### 3.5 서버·CLI

`NamingRulesSchema` 에 `tableLogicalTemplate: z.string().default('')`,
`NamingRulesStrictSchema` 에 `tableLogicalTemplate: z.string()`(기본값 주입 금지).

⚠️ **strict 쪽을 빠뜨리면 조용한 데이터 손실이다** — `.default('')` 를 물려받으면 키를 안 보낸
`project.update` 가 설정해 둔 템플릿을 지운다. 직전 사이클이 같은 자리에서 실증으로 잠갔다.

CLI `config.ts` 는 물리명 템플릿과 같은 형태 — 임의 문자열이라 검증하지 않고 누락만 `''` 로 채운다.

## 4. 테스트

**core — 접기 규칙(교체)**
- ⚠️ **기존 6형이 그대로인지**가 급소다. 하나라도 결과가 바뀌면 회귀다.
- 새 2형(`TB_{그룹별칭}_LOG` → `TB_LOG`, `{그룹별칭}_LOG_{물리명}` → `LOG_ORD`)
- **뒤에서부터 훑기**: `A_{X}_{Y}` 둘 다 빔 → `A`(직전 조각만 보면 `A_` 가 나온다)
- **변수 값은 안 건드린다**: 물리명이 `ORD_` 로 끝나고 뒤 변수가 빌 때 `ORD_` 가 보존된다

**core — 논리명 조합**
- 템플릿이 `''` 면 `logicalName` 을 그대로 낸다(기존 동작 보존)
- 변수 5종 · 알 수 없는 변수는 빈 값 · 접기
- **`{물리명}` 을 참조해도 조합 물리명이 아니라 부분을 쓴다**(재귀 없음을 잠근다)

**core — 소비처**
- DDL 코멘트 2방언(mysql 인라인 / `COMMENT ON`)이 조합 논리명을 쓴다
- ⚠️ **생략 판정이 조합끼리 비교된다**(D5) — D5 표의 입력(그룹명 `SALES`, 논리명=물리명=`ORD`,
  두 템플릿 모두 `{그룹명}_…`)을 그대로 쓴다. 조합끼리면 코멘트가 없고, 논리명만 부분으로
  되돌리면 코멘트가 생긴다
- `warningLabel` 폴백 · DBML note · Excel 논리명 열 2자리
- ⚠️ **`warnings.ts` 결과가 안 바뀌는지** — 논리명 템플릿을 걸어도 용어·미등록 단어·구분자 경고가
  그대로여야 한다(D1 의 근거를 잠근다)

**server** — `tableLogicalTemplate` 없는 기존 행에 `''` 주입 · 키 뺀 `update` 거절

**web** — 설정 두 번째 입력란·미리보기 / 편집 패널 논리명 미리보기(컬럼에는 안 뜬다)

**잠기지 않는 것 (명시)**
- **논리명 쪽 왕복 깨짐**은 물리명 D2 와 같은 성질이라 별도 테스트를 만들지 않는다 — 다음 사이클이
  둘을 함께 닫는다. 물리명 쪽 고정 테스트(`ddl-import.test.ts`)가 이미 재검토를 강제한다.

## 6. 이월 (이 사이클에서 구현하지 않는다)

- **역설계 역분해 — SQL 코멘트 메타정보안(다음 사이클 후보).** 조사 결과 **기술적으로 가능하고
  이 저장소에 선례가 있다**: `buildDbmlNote`/`splitDbmlNote` 가 커스텀 항목 값을 note 끝에 JSON
  꼬리(`{"보안등급":"2"}`)로 실어 왕복시킨다. DDL 도 같은 구조다 — `commentText` 가
  `'논리명 - 설명'` 을 만들고 `splitComment` 가 첫 ` - ` 에서 되쪼개며, 파서는 네 방언의 코멘트를
  전부 `parsed.comments` 로 뽑는다(PostgreSQL·Oracle `COMMENT ON`, MySQL 인라인/꼬리 `COMMENT=`,
  MSSQL `sp_addextendedproperty`). 그러니
  `COMMENT ON TABLE TB_MBR_ORD IS '주문 {"물리부분":"ORD","논리부분":"주문"}'` 로 실으면 **추측 없이**
  되찾고, 꼬리가 없으면(남의 DDL·사용자가 지운 경우) 지금 동작으로 자연스럽게 떨어진다.
  **결정할 것 셋:** (a) 꼬리를 테이블마다 둘지 덤프 머리말 한 곳에 둘지, (b) 논리명==조합이라
  지금은 코멘트를 안 내는 테이블에도 메타를 위해 코멘트를 강제로 낼지(DDL 노이즈), (c) 템플릿 자체도
  실을지 부분만 실을지. **이 사이클이 논리명 템플릿을 넣으므로 payload 는 논리·물리 둘 다 실어야 한다.**
- **컬럼 논리명·물리명 템플릿** — 요청 밖.
- **CLI 파일에 최종 이름 노출** — 부분만 싣는다. `erdd validate` 의 경고는 최종 이름 기준이라
  파일에 보이는 이름과 경고 문구가 다를 수 있다(물리명 사이클에서 수용).
- **`project-settings.tsx` 의 `template === '' → null` 가드 미잠금** — 물리명 쪽에서 이월된 것이고,
  이 사이클이 같은 모양의 입력란을 하나 더 만들므로 **둘을 함께 잠글지 판단한다.**
