# 대용량 라이브러리 조회·편집 개선과 5,000건 분할 적용

## 배경과 목표

**지금 막히는 곳**

행안부 공통표준(도메인 126 · 단어 3,280 · 용어 13,159, 합계 16,565건)을 전역 라이브러리로 넣자 화면이
눈에 띄게 느려졌다.

- **관리 화면과 에디터가 라이브러리 항목 전체를 한 번에 받는다.** `resource.items.list` 는 페이지 없이
  16,565건을 돌려주고, 관리 화면(`ResourceLibraryManager`)은 그것을 종류별로 `filter` 해 `<li>` 로 전부
  그린다. 가상화도 페이지도 없다.
- **에디터 사전 목록이 행마다 모델 전체를 훑는다.** `DictPanel` 은 단어·용어 행 하나마다
  `wordUsage`/`termUsage` 를 부르고, 둘 다 모든 테이블·컬럼을 순회한다(`wordUsage` 는 그 안에서 논리명
  분해까지 한다). 비용이 사전 행 수 × (테이블 + 컬럼)이다.
- **재동기화·승격 화면이 구역별 항목을 전부 체크박스로 그린다.** 16,565건이면 체크박스가 1.6만 개다.
- **5,000건 상한이 대량 적용을 막는다.** 재동기화 적용·Excel 사전 가져오기·일괄 삭제·DDL 가져오기·승격이
  `MAX_OPS_PER_MUTATION`(5000)을 넘으면 버튼을 잠그고 「나눠 선택하라」고 안내한다. 공통표준을 프로젝트에
  한 번에 받을 수 없다.
- 항목 수에 천 단위 구분자가 없고(`항목 16565개`), 관리 화면 행에는 이름 하나만 보여 물리명을 알 수 없다.

**사용자 결정**

| 질문 | 결정 |
|---|---|
| 관리 화면의 라이브러리 조회 | 라이브러리를 누르면 **조회 모달**이 열린다. 단어·용어·도메인·커스텀 항목 **탭**, 탭마다 **페이지** |
| 이름 표시 | **논리명과 물리명을 함께** 보인다 |
| 에디터 사전·리소스 팝업 | 같은 방식(탭·페이지·표시)으로 전반 개선 |
| 5,000건 상한 | 상한을 두지 말고 **나눠 요청**해서 처리한다 |
| 나눠 보냈을 때의 실행 취소 | **실행 취소 1회로 전부 되돌린다.** 서버 이력(Revision)은 조각 수만큼 쌓여도 된다 |
| 검색 | 탭마다 **검색창**을 둔다(논리명·물리명 부분 일치) |

**목표가 아닌 것**

- 목록 가상화. 사용자가 페이지 방식을 골랐다. 페이지 크기가 작으면 가상화 없이도 DOM 이 작다.
- CLI 가 쓰는 `resource.items.list` 의 형태 변경. CLI(`dict pull`·`dict push`·`library`)가 전체 목록을
  전제로 `planPromote`·`planResync` 를 돌리므로 그대로 둔다.
- 서버의 모델 입력 상한(`model.mutate`·`model.push` 의 `ops` 최대 5,000) 완화. 요청 하나의 크기는 계속
  제한한다 — 본문 크기·트랜잭션 시간·실시간 방송 크기를 예측 가능하게 두고, CLI `push` 도 같은 상한을 쓴다.

## 1. 표시 규칙 — 논리명·물리명과 숫자

**종류별 이름 두 칸**을 core 에 한 벌 둔다. 관리 모달·에디터 패널·재동기화·승격 화면이 모두 이 함수로
행을 그린다 — 화면마다 payload 를 따로 읽으면 한쪽만 바뀐다.

| 종류 | 논리명 칸 | 물리명 칸 | 보조 칸 |
|---|---|---|---|
| 단어 | `logicalName` | `abbreviation` | `englishName` |
| 용어 | `logicalName` | `physicalName` | 도메인 이름 |
| 도메인 | `name` | (없음) | `category` · `logicalType` |
| 커스텀 항목 | `name` | (없음) | `target` · `type` |

- core `resource.ts` 에 `resourceSecondaryName(kind, payload): string | null` 을 더한다(단어는
  `abbreviation`, 용어는 `physicalName`, 나머지 `null`). 기존 `resourceDisplayName` 은 그대로 논리명 칸이다.
- 재동기화·승격 행은 이미 실린 payload(`ResyncEntry` 의 `sourcePayload`/`nextPayload`, `PromoteEntry` 의
  프로젝트 엔티티)에서 물리명을 읽는다. 계획 타입에 새 필드를 더하지 않는다.
- **숫자 표시 헬퍼** `formatCount(n)`(`apps/web/src/lib/format.ts`, `ko-KR` 천 단위 구분)를 두고 **항목 수·
  건수 표시 전부**가 쓴다 — 관리 화면 목록, 삭제 확인 문구, 공용 리소스 패널 라이브러리 목록, 탭 제목의 개수,
  페이지 표시, 적용 진행 표시, 토스트 요약.

## 2. 서버 — 페이지 조회와 종류별 개수

### `resource.items.page` (신설)

```ts
input:  { libraryId: string; kind: ResourceKind; query?: string; offset: number; limit: number }  // limit 1..200
output: { items: { id; kind; payload; version }[]; total: number }
```

- **권한은 `items.list` 와 같은 판정**을 쓴다(같은 헬퍼를 부른다). 한쪽만 고치면 볼 수 없는 라이브러리가
  한쪽 경로로 새어 나간다.
- **검색**: `query` 를 `trim` 해 비어 있으면 거르지 않는다. 있으면 대소문자를 무시한 부분 일치(`ILIKE`,
  `%`·`_`·`\` 는 이스케이프)로 다음 필드 중 하나라도 맞으면 고른다.
  단어 `logicalName`·`abbreviation`·`englishName`, 용어 `logicalName`·`physicalName`, 도메인·커스텀 `name`.
- **정렬**: 논리명 칸(`logicalName` 또는 `name`) 오름차순, 같으면 `id`. 같은 입력에 같은 순서가 나와야
  페이지를 넘길 때 항목이 겹치거나 빠지지 않는다.
- `total` 은 같은 조건의 전체 건수다(페이지 수 계산용).
- 이 프로시저는 **`apiProcedure` 로 열지 않는다**(세션 전용). 토큰 소비처가 없다 — CLI 는 `items.list` 를 쓴다.
  토큰에 여는 것은 명시적 opt-in 이라는 규칙(`guides/cli.md`)을 따른다.

### `library.list`·`library.listForProject` 에 `countsByKind`

- 공통 조회 `listWithCounts` 가 `itemCount` 와 함께 `countsByKind: Record<ResourceKind, number>` 를 낸다
  (`count(*) filter (where kind = …)`). 탭 제목의 개수와 빈 탭 표시에 쓴다.
- `itemCount` 는 남긴다(CLI `dict list`·`library list` 가 쓴다).

### 인덱스

- 마이그레이션으로 `resource_items (library_id, kind)` 복합 인덱스를 더한다. 기존 `ix_resource_items_library_id`
  는 복합 인덱스의 앞 열과 겹치므로 지운다.
- 이름은 jsonb 안에 있어 정렬·검색은 인덱스를 타지 않는다. 한 라이브러리·한 종류가 수만 건 수준이라
  (library_id, kind) 로 좁힌 뒤의 정렬·필터로 충분하다. 식 인덱스는 넣지 않는다.

## 3. 관리 화면 — 라이브러리 조회 모달

`ResourceLibraryManager`(전역·조직 공통)를 고친다.

- **목록 행**: `〈설명〉 · 항목 16,565개`. 행을 누르면 지금처럼 아래로 펼치지 않고 **「라이브러리 조회 —
  〈이름〉」 모달**을 연다. 내보내기·가져오기·삭제 버튼은 목록 행에 그대로 둔다.
- **모달**
  - 탭: 「단어 (3,280)」·「용어 (13,159)」·「도메인 (126)」·「커스텀 항목 (0)」. 처음 열 때는 첫 탭(단어)이다.
  - 탭마다 검색창(입력 300ms 디바운스)과 표, 아래에 페이지 이동. 페이지 크기 50.
  - 검색어를 바꾸면 1페이지로 간다. 탭을 바꾸면 그 탭의 검색어·페이지는 탭별로 유지한다.
  - 표 열은 1절의 표를 따른다. 끝 열에 버전(`v3`), 관리 권한이 있으면 편집·삭제 버튼.
  - 관리 권한이 있으면 탭마다 「추가」 버튼. 추가·편집은 기존 `ResourceItemForm` 을 쓴다.
  - 결과가 없으면 「검색 결과가 없습니다」(검색 중) / 「항목이 없습니다」(빈 탭).
- **데이터**: 탭의 표는 `items.page` 로 받는다. `items.list` 는 이 화면에서 부르지 않는다.
  - 용어 폼의 도메인 선택지는 **도메인 전체**가 필요하다. 폼을 열 때 `items.page({kind: 'domain', limit: 200})`
    를 페이지 끝까지 받아 쓴다(도메인은 수백 건 수준). 용어 표의 「도메인」 칸도 이 목록으로 id → 이름을 푼다.
  - 추가·편집·삭제 뒤에는 `items.page`·`library.list` 를 함께 무효화한다(지금 `items.update` 뒤에
    `library.list` 를 빼먹는 것도 이때 맞춘다 — 개수는 안 바뀌지만 무효화 규칙을 하나로 둔다).
- **라이브러리 가져오기 다이얼로그**(`LibraryImportDialog`)가 기존 라이브러리의 항목 전체를 받는 조회를
  걷는다. 미리보기는 이미 서버(`library.import` dryRun)가 계산하므로 필요한 것은 그 응답과 `countsByKind` 로
  대신한다. 구현 시 그 조회가 무엇에 쓰이는지 확인하고, 대체할 수 없는 쓰임이 있으면 보고한다.

## 4. 에디터 사전·리소스 팝업

모델이 이미 메모리에 있으므로 **클라이언트에서 거르고 페이지를 나눈다.** 서버 조회는 늘리지 않는다.

### 공용 UI 부품

- `components/ui/tabs.tsx` — shadcn Tabs(`radix-ui` 에 이미 있는 Tabs 프리미티브). ARIA tablist 를 갖춘다.
- `components/ui/pagination.tsx` — 「이전 · 3 / 263 · 다음」과 전체 건수(`formatCount`)를 보이는 작은 부품.
  페이지가 1쪽뿐이면 숨긴다.
- `lib/paginate.ts` — `filterAndPage(rows, query, fields, page, size)` 순수 함수. 에디터 패널들이 함께 쓴다.

### 단어·용어 사전(`DictPanel`)

- 버튼으로 흉내 내던 섹션 전환을 Tabs 로 바꾼다(단어·용어·미등록·가져오기).
- 단어·용어 탭에 검색창과 페이지(50건). 검색 필드는 2절 서버 검색과 같다.
- 행은 논리명과 물리명을 **한 줄에 나란히**(논리명 | 물리명 | 사용 수) 보인다.
- **사용처 색인**: 행마다 `wordUsage`/`termUsage` 를 부르지 않는다. 모델을 **한 번** 훑어
  `buildUsageIndex(model, namingRules) → { words: Map<id, Usage>, terms: Map<id, Usage> }` 를 만들고,
  `useMemo` 로 모델·명명 규칙이 바뀔 때만 다시 만든다. 행은 색인에서 읽는다.
  - **색인의 결과는 기존 `wordUsage`/`termUsage` 와 같아야 한다.** 삭제 확인처럼 한 건만 필요한 곳은 기존
    함수를 계속 써도 되므로, 두 경로가 갈리면 목록의 사용 수와 삭제 경고가 서로 다른 수를 말한다. 같은
    픽스처에서 모든 id 에 대해 두 경로가 같은 값을 내는지 테스트로 잠근다.

### 도메인(`DomainPanel`)·커스텀 항목(`CustomFieldPanel`)

- 검색창과 페이지를 더한다. 도메인의 분류 묶음 표시와 커스텀 항목의 대상별 구분·순서 버튼은 유지한다
  (페이지는 거른 뒤의 전체 행 기준으로 나누고, 묶음 제목은 그 페이지에 나오는 묶음만 그린다).
- 커스텀 항목의 순서 버튼은 **검색 중에는 잠근다** — 걸러진 목록에서 「위로」는 사용자가 보는 이웃이 아닌
  숨은 이웃과 자리를 바꾼다.

### 공용 리소스 — 가져오기(재동기화)·승격

- 라이브러리 목록의 개수에 `formatCount`, 탭은 Tabs 부품으로 바꾼다.
- 구역(신규 추가·자동 갱신·충돌 / 신규 추가·원본 갱신·동명 발견)마다 검색창과 페이지(50건)를 둔다.
  행에는 종류 배지·논리명·물리명을 보인다(1절).
- **선택 상태는 구역 전체에 대해 유지한다.** 페이지를 넘겨도 체크가 남는다. 「모두 선택/해제」(충돌은
  「모두 원본 반영/모두 프로젝트 유지」)는 **보이는 페이지가 아니라 구역 전체**에 적용한다 — 지금 동작과
  같다. 검색 중에도 구역 전체다(버튼 옆에 「구역 전체 N건에 적용」을 적어 오해를 막는다).
- 승인 다이얼로그(`promotion-requests-section`)도 같은 `PromoteEntryList` 를 쓰므로 함께 바뀐다.

## 5. 5,000건을 넘는 모델 편집 — 나눠 보내기

### 규칙

**나누는 곳은 모델 변경의 저수준 단일 경로(`use-model.ts`) 한 곳이다.** 정상 편집·실행 취소·다시 실행이
모두 이 경로를 지나므로, 여기서 나누면 재동기화 적용·Excel 사전 가져오기·일괄 삭제·DDL 가져오기와 그 실행
취소·다시 실행이 한꺼번에 풀린다. 소비처는 나눔을 모른다.

1. producer 로 다음 모델을 만들고 `diffModels` → `validateModelIntegrity` 까지는 지금과 같다.
2. op 가 `MAX_OPS_PER_MUTATION` 이하이면 지금과 똑같이 한 번 보낸다.
3. 넘으면 **`diffModels` 가 낸 순서 그대로** `MAX_OPS_PER_MUTATION` 씩 잘라 `model.mutate` 를 **차례로** 부른다.
   요약은 `〈원래 요약〉 (1/4)`·`(2/4)`… 로 조각 번호를 붙인다.
4. 낙관적 반영은 지금처럼 **처음에 한 번**(전체 다음 모델) 한다.
5. 모든 조각이 성공하면 **실행 취소 기록은 편집 1건 = 전체 `Op[]` 하나**다(`recordEdit(ops)` 한 번).
   실행 취소·다시 실행은 그 `Op[]` 의 역연산을 같은 경로로 보내므로 역시 조각으로 나뉘어 간다.
   사용자는 한 번 누른다.
6. 전역 직렬화 체인(`serializeMutation`) 안에서 조각을 모두 보낸다 — 그 사이 내 다른 편집·실행 취소는
   체인 뒤에 줄을 선다.

### 조각 순서가 정확성 조건인 이유

`diffModels` 는 FK 안전 순서(`ENTITY_KINDS` 순서, 추가는 부모 먼저 · 삭제는 자식 먼저)로 op 를 정렬한다.
서버는 조각 하나를 독립된 mutation 으로 적용하므로 **각 조각까지 적용된 중간 상태가 모두 무결성을 만족해야
한다.** 즉 「`diffModels` 결과의 **모든 접두사**를 적용한 모델이 `validateModelIntegrity` 를 통과한다」가
이 설계가 기대는 불변식이다. 구현은 이 불변식을 먼저 테스트로 확인한다(도메인 추가 + 그 도메인을 가리키는
용어 추가, 테이블 삭제 + 그 테이블을 가리키는 관계 삭제처럼 참조가 걸린 대량 diff 를 5,000 경계가 참조
사이에 오도록 만들어 모든 조각 경계에서 검사). **불변식이 깨지는 경우가 있으면 구현을 멈추고 보고한다** —
조각 경계를 참조 단위로 조정할지는 그때 판단한다.

### 실행 중 표시

- 조각이 둘 이상이면 해당 다이얼로그의 적용 버튼을 잠그고 「적용 중… 2 / 4」를 보인다. 저수준 경로가
  진행 콜백(`onProgress(done, total)`)을 받아 소비처가 표시한다.
- 조각이 하나뿐이면 지금과 똑같이 보인다.

### 실패와 경합

- **중간 조각이 실패하면** 거기서 멈추고 서버 최신 상태로 다시 맞춘다(`resync`). 실행 취소 기록은 비워진다
  (`resync` 의 기존 동작). 토스트: 「4개 묶음 중 2개를 적용했고 나머지는 적용하지 못했습니다 — 〈오류〉」.
  반쯤 들어간 편집을 「한 번에 되돌리기」로 기록하지 않는다 — 되돌릴 op 가 실제 서버 상태와 어긋난다.
- **첫 조각이 실패하면** 지금의 단일 mutation 실패와 똑같이 처리한다(서버 상태로 되맞춤, 오류 토스트).
- **조각 사이에 남의 편집이 끼어들면**(응답 `seq` 가 기대값 + 1 이 아님) 남은 조각을 계속 보낸다 — 조각은 op
  단위로 적용되고, 남의 편집과 겹쳐 거절되면 위의 중간 실패로 간다. 모든 조각이 끝나면 지금의 seq 간극
  경로와 같이 서버 최신 모델로 `resync` 한다.
- 조각 도중 프로젝트를 떠나면(`loadedProjectId` 가 바뀜) 남은 조각을 보내지 않는다(지금의 가드와 같은 자리).

### 걷는 것

- 5,000건 사전 차단과 문구 넷: 재동기화·승격의 `overLimitMessage`(「한 번에 5000건까지 적용할 수 있습니다…」),
  Excel 사전 가져오기의 `tooManyOps`, 일괄 삭제의 `tooBig`(「한 번에 지우기에 너무 많습니다」), DDL 가져오기의
  `overLimit`. 해당 테스트의 상한 단언은 「상한을 넘어도 적용되고 조각으로 나뉘어 간다」로 바꾼다.

## 6. 승격과 승격 요청

### 직접 승격(`resource.promote`)

- 승격은 모델 편집 경로가 아니라 서버가 라이브러리와 프로젝트 `origin` 을 함께 쓰는 별도 프로시저다.
  입력 `entries` 상한(5,000)은 그대로 두고, **클라이언트가 선택 항목을 5,000건씩 잘라 차례로 부른다.**
- 자르는 순서는 계획의 항목 순서(종류: 도메인 → 단어 → 용어 → 커스텀)를 따른다. 용어의 도메인 연결은
  서버가 락 안에서 계획을 재계산할 때 앞 조각에서 올라간 도메인을 본다.
- 결과(추가·갱신·건너뜀)는 조각별 응답을 합쳐 토스트 하나로 보인다. 진행 표시는 5절과 같다.
- 중간 실패 시 「N건 중 M건 승격했습니다 — 〈오류〉」를 보이고 계획을 다시 불러온다.
- 승격은 지금도 에디터 실행 취소 대상이 아니다 — 이 동작은 바뀌지 않는다.

### 승격 요청(`promotion.create`)·승인(`promotion.resolve`)

- 요청은 엔티티 id 목록을 저장할 뿐이고, 승인은 서버가 한 트랜잭션으로 반영한다. 모델 op 상한과 무관하므로
  **나누지 않고 입력 상한을 50,000 으로 올린다**(라이브러리 파일 상한 `MAX_LIBRARY_FILE_ITEMS` 와 같은 값을
  공유 상수로 쓴다). 요청을 여러 개로 쪼개면 승인자가 같은 요청을 여러 번 검토해야 한다.
- 승인 반영은 서버 안에서 `mutateAndPublish` 로 가며 op 수 검사가 없다. 대량 승인의 실시간 방송 크기가
  커지는 것은 알려진 한계로 적는다.

## 7. 문서 갱신

- `docs/guides/data-layer.md` 「한 뮤테이션의 op 상한은 `MAX_OPS_PER_MUTATION`(5000)이다」: 상한은 **요청
  하나**의 상한이고, 웹의 모델 변경 저수준 경로가 넘는 편집을 나눠 보낸다는 것, 「편집 1건 = 실행 취소 1회」는
  유지되지만 「Revision 1건」은 조각 수만큼이 된다는 것, 조각 순서(모든 접두사 무결성)가 정확성 조건이라는 것.
- `docs/guides/shared-resources.md`: 재동기화 적용의 「Revision 1건, undo 1회」 서술, 승격 조각 처리,
  승격 요청 상한.
- `docs/manual/user-guide.md`: 13절(재동기화 5,000건 제약 문구), 16절(Excel 가져오기 상한 문구), 20절(일괄
  삭제 상한 문구), 19절(라이브러리 관리 — 조회 모달·탭·검색·페이지), 사전 패널 설명. 나눠 적용될 때의 진행
  표시와 중간 실패 안내를 적는다.
- `docs/manual/local-guide.md`: 로컬 모드는 로컬 라우터를 쓰므로 나눠 보내기가 같은 경로로 동작하는지
  확인하고, 대조표가 어긋나면 고친다.
- 코드 주석 중 「Revision 1건·undo 1회」를 말하는 것(`resource-resync-tab.tsx`·`dict-import-section.tsx`·
  `dict-import-edits.ts`·`op-guard.ts` 등)을 새 규칙에 맞춘다. 착수 시 `grep -rnE "Revision 1건|undo 1회|
  undo 한 번|5000건|MAX_OPS_PER_MUTATION"` 으로 목록을 만들어 태스크에 배분한다.

## 8. 테스트

| 대상 | 잠그는 것 |
|---|---|
| core `resourceSecondaryName` | 종류별 물리명 칸 |
| web `formatCount` | `16565 → "16,565"` |
| server `items.page` | 권한(볼 수 없는 라이브러리 거절), 종류 필터, 검색 필드별 일치·이스케이프(`%`·`_`), 정렬 안정성(두 페이지가 겹치지도 빠지지도 않음), `total` |
| server `library.list` | `countsByKind` 가 종류별 개수와 합이 `itemCount` 와 같음 |
| web 조회 모달 | 탭 개수 표시, 검색 → 1페이지, 페이지 이동이 `offset` 을 바꿔 부름, 권한 없으면 편집 버튼 없음 |
| web `buildUsageIndex` | 같은 픽스처에서 모든 단어·용어 id 에 대해 `wordUsage`/`termUsage` 와 같은 값 |
| web 에디터 패널 | 검색·페이지, 커스텀 항목 검색 중 순서 버튼 잠김 |
| web 재동기화·승격 목록 | 페이지를 넘겨도 선택 유지, 「모두 선택」이 구역 전체에 적용 |
| core diff 접두사 | 5절 「모든 접두사 무결성」 |
| web 저수준 경로 | 5,000 이하 한 번, 초과 시 조각 수·순서·요약 번호, 실행 취소 1회가 역연산을 조각으로 보냄, 중간 실패 시 멈춤·resync·토스트, 조각 사이 seq 간극 시 끝까지 보낸 뒤 resync, 프로젝트 이탈 시 중단 |
| web 승격 | 5,000 초과 선택이 조각으로 나뉘어 불리고 결과가 합쳐짐 |
| server `promotion.create` | 5,001건 요청이 받아들여짐, 50,001건 거절 |

**구분력**: 각 수정은 프로덕션 변경을 되돌리면 해당 테스트가 실패하는지 커밋 뒤에 확인한다
(`guides/worktree-workflow.md` 「구분력 실증은 반드시 커밋 뒤에 한다」).

**스모크**: 실 앱 + 실 DB 에 공통표준 라이브러리(16,565건)를 넣고 — ① 관리 화면 모달의 탭·검색·페이지,
② 빈 프로젝트에서 재동기화로 16,565건 전체 적용(조각 4개, 진행 표시) → 사전 패널 열림 속도 → 실행 취소 한 번에
전부 사라짐 → 다시 실행, ③ 승격 5,000건 초과를 확인한다.

## 알려진 한계

- **나눠 적용 중 중간 실패는 원자적이지 않다.** 앞 조각은 서버에 남고, 실행 취소 기록은 비워진다. 되돌리려면
  이력(버전) 화면에서 이전 스냅샷으로 돌아간다.
- **서버 이력은 조각 수만큼 쌓인다.** 요약의 `(1/4)` 표시로 묶음을 알아볼 수 있을 뿐 이력 화면이 묶어
  보이지는 않는다.
- **대량 편집의 실시간 방송**은 조각마다 한 번이다. 다른 참여자의 화면은 조각 단위로 바뀐다.
- **대량 승인(`promotion.resolve`)은 한 트랜잭션이라 방송 크기에 상한이 없다.**
- **정렬은 DB 정렬 규칙을 따른다.** 서버 정렬(관리 모달)과 에디터의 `localeCompare` 정렬이 한글·영문 혼합에서
  미세하게 다를 수 있다.
