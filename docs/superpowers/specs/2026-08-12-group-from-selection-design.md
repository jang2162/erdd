# 선택 테이블로 새 그룹 만들기 — 설계

**작성:** 2026-08-12 / **상태:** 사용자 확정 / **마이그레이션:** 없음 / **서버 변경:** 없음 / **core·CLI 변경:** 없음

---

## 1. 목적과 범위

캔버스에서 shift+드래그(박스 선택)나 사이드바 shift+클릭으로 테이블 여러 개를 고른 다음, **우측
사이드바에서 그것들을 담는 그룹을 바로 만든다.**

지금은 길이 둘로 갈라져 있고 둘 다 그 일을 못 한다.

- 좌측 사이드바 「그룹 추가」(`table-tree.tsx:135`)는 **빈 그룹**만 만든다. 선택과 무관하다.
- 우측 `BulkPanel`의 「선택 테이블의 그룹」 드롭다운은 **이미 있는 그룹으로만** 옮긴다.

그래서 "이 다섯 개를 묶고 싶다"는 의도가 세 단계로 쪼개진다 — 빈 그룹을 만들고(선택이 풀린다),
테이블을 다시 고르고, 드롭다운에서 그 그룹을 찾아 옮긴다. Revision도 2건이라 `cmd+Z` 한 번으로
되돌아가지 않는다.

**범위 안**

- `BulkPanel`의 버튼 1개와 그 동작
- "새 그룹 하나 만들기" 규칙을 담을 신설 모듈 `apps/web/src/editor/group-edits.ts`
- 좌측 「그룹 추가」를 그 모듈로 옮기는 리팩터(동작 불변)

**범위 밖 (건드리지 않는다)**

- `packages/core` — `createGroup`·`setTableGroup`이 이미 있고 새로 필요한 것이 없다
- 서버·마이그레이션 — 기존 `model.mutate` op 파이프라인을 그대로 탄다
- CLI·파일 포맷·DDL·DBML·Excel — 결과물이 **평범한 그룹 1개와 테이블의 `groupId`**뿐이라 이들이
  새로 알아야 할 것이 없다
- 좌표 재배치(2절 D2) · 캔버스 컨텍스트 메뉴 · 단축키 — 진입점은 우측 패널 버튼 하나다

## 2. 확정된 결정 (사용자 확정)

### D1. 자동 이름으로 즉시 만들고, 이름은 그룹 패널에서 고친다

버튼을 누르면 다이얼로그 없이 곧바로 만들어진다. 이름은 **미사용 최소 번호** `그룹N`, 색은
`nextGroupColor(사용 중인 색들)` — **좌측 「그룹 추가」와 같은 규칙이다.** 만든 뒤 우측이 그룹
패널로 전환되므로 이름·색상·설명을 그 자리에서 고칠 수 있다.

**왜:** 이름 입력 다이얼로그를 두면 컴포넌트와 열림 상태가 하나 더 늘고, 정작 사용자는 그 뒤에
같은 값을 그룹 패널에서 다시 고친다. 기존 진입점과 규칙이 한 벌로 유지되는 것도 이 안이다 —
다이얼로그를 우측에만 붙이면 같은 "새 그룹"이 어디서 만드느냐에 따라 이름이 다르게 정해진다.

**따라오는 것:** `selectGroup`은 `CLEARED_SELECTION`을 적용하므로 **테이블 선택이 풀린다.** 의도된
결과다 — 우측 패널이 `BulkPanel`(테이블 2개 이상)과 `GroupPanel`(그룹 선택) 중 하나만 그릴 수
있고(`edit-panel.tsx:72-80`), 방금 만든 그룹의 이름을 고치는 것이 그 시점의 다음 행동이다.

### D2. 좌표는 건드리지 않는다

새 그룹의 멤버는 선택한 테이블 전부이므로 테이블은 **지금 자리에 그대로 있고 그 위에 색상 영역만
씌워진다.**

**왜:** `planGroupMove`는 "대상 그룹의 **기존** 멤버 bbox 오른쪽으로 옮긴다"는 함수다. 새 그룹에는
기존 멤버가 없어 기준 bbox가 없고, 그래서 그 함수는 이 경우 **정의상 빈 배열을 낸다**(`group-move.ts:128`).
없는 기준을 만들어 내려면 "선택 집합을 어디에 어떻게 모을 것인가"라는 새 배치 규칙이 필요한데,
그것은 사용자가 잡아 둔 배치를 뭉개는 일이다. shift+드래그 박스 선택은 애초에 **화면상 모여 있는
것**을 고르므로 흔한 경우에는 문제도 없다.

**한계(수용):** 사이드바에서 멀리 떨어진 테이블을 shift+클릭으로 고르면 그것들을 감싸는 큰 사각형이
생기면서 **그 안의 남의 테이블까지 시각적으로 품는다.** 사용자가 보고 직접 끌어 정리한다. 6절에
남긴다.

**구현 지침:** `planGroupMove`를 **부르지 않는다.** 어차피 빈 배열이지만, 부르지 않아야 "제자리가
의도"임이 코드에 드러나고 `columnCounts`의 컬럼 전수 스캔도 돌지 않는다.

### D3. 이미 다른 그룹에 속한 테이블도 그대로 데려간다

선택에 다른 그룹 멤버가 섞여 있어도 확인 없이 새 그룹으로 옮긴다. 드롭다운 이동·사이드바 드롭·
캔버스 드롭이 모두 그렇게 동작하므로, 여기만 확인을 붙이면 같은 의도가 진입점에 따라 다르게
끝난다. 되돌리기는 `cmd+Z` 한 번이다(D4).

## 3. 구조

### 3.1 신설 모듈 `apps/web/src/editor/group-edits.ts`

"새 그룹 하나 만들기"의 규칙은 지금 `table-tree.tsx`의 `onAddGroup` **안에 인라인**으로 있다.
진입점이 둘이 되므로 한 곳으로 옮긴다 — `applyGroupMove`가 세 진입점(드롭다운·사이드바 드롭·캔버스
드롭)의 규칙을 한 곳에 모아 둔 것과 같은 형태다. 복붙하면 한쪽만 고쳐질 자리가 생긴다.

```ts
/**
 * 새 그룹을 만들고 주어진 테이블을 그 그룹에 넣는다. `tableIds`가 비면 빈 그룹이다
 * (좌측 사이드바 「그룹 추가」가 그 경로다).
 *
 * 반환값은 새 그룹 id — 권한이 없으면 null. 호출자가 `selectGroup`에 쓴다.
 */
export function createGroupWith(mutate: Mutate, tableIds: readonly string[]): string | null
```

**함수가 하는 것**

1. `canEdit` 가드 — `useEditorStore.getState().canEdit`이 false면 아무것도 하지 않고 `null`.
   `applyGroupMove`와 같은 자리에 둔다(호출자마다 붙이면 두 벌이 된다).
2. `newId()`로 id 발급. **producer 밖이어야 한다** — 반환해야 하는 값이기 때문이다.
3. producer 하나 안에서:
   - 이름·색을 **producer가 받은 모델 `m`에서 계산한다.** 미사용 최소 `그룹N`, `nextGroupColor`.
     store 스냅샷이 아니라 `m`을 쓰는 것이 옳다 — 낙관적 체인에서 앞선 뮤테이션이 이미 그룹을
     만들었을 수 있다(현행 `onAddGroup`은 store에서 읽으므로 이 리팩터가 함께 고치는 결함이다).
   - `createGroup(m, { id, name, color })`
   - 테이블마다 `setTableGroup(next, tid, id)` + `clearTableGroupPosition(next, tid)`
4. `summary`는 멤버 유무로 갈린다 — `그룹 추가 (테이블 N개)` / `그룹 추가`.

**`clearTableGroupPosition`이 필요한 이유**는 `applyGroupMove`의 ⚠️와 같다. 테이블은 좌표를 둘
갖는다(전체 뷰 `position`, 그룹 뷰 전용 `groupPosition`). 옛 그룹 뷰 좌표를 남겨 두면 새 그룹의
그룹 뷰에서 멤버가 갈라진다 — 옛 그룹에 있던 것은 옛 좌표, 미분류였던 것은 폴백 좌표에 선다.
전원 비워야 `buildNodes`가 모두 전체 뷰 좌표로 폴백해 나란히 선다.

**`Mutate` 타입**(`ReturnType<typeof useModelMutation>`)은 지금 `bulk-panel.tsx`가 로컬로 갖고 있다.
`group-edits.ts`가 같은 선언을 복제하지도, `bulk-panel.tsx`에서 가져오지도 않는다 — 후자는
`bulk-panel → group-edits → bulk-panel` 순환이 된다(타입 전용이라 런타임 순환은 아니지만 방향이
거꾸로다). **선언을 `use-model.ts`로 올려 export하고 두 파일이 거기서 가져온다** — 둘 다 이미
`use-model.js`를 import하고 있고, 타입의 출처는 원래 그 파일이다.

**선택 전환은 함수 밖이다.** `createGroupWith`는 store의 선택 상태를 건드리지 않는다 —
`applyGroupMove`가 그렇듯 모델만 바꾼다. 두 호출자가 각자 `selectGroup(id)`를 부른다.

### 3.2 `BulkPanel` (`bulk-panel.tsx`)

그룹 드롭다운 바로 아래, 삭제 버튼 위에 버튼 하나를 넣는다.

```
선택 테이블의 그룹  [ 미분류 ▾ ]
[ 선택 테이블로 새 그룹 ]        ← variant="outline", w-full, disabled={!canEdit}
[ 선택 테이블 삭제 ]              ← 기존
```

`onClick`은 두 줄이다 — `createGroupWith(mutate, ids)`를 부르고, 반환된 id가 있으면
`selectGroup(id)`.

### 3.3 `TableTree` (`table-tree.tsx`)

`onAddGroup`의 본문을 `createGroupWith(mutate, [])` + `selectGroup(id)`로 교체한다. `createGroup`·
`newId`·`nextGroupColor` import가 이 파일에서 빠진다. **동작은 불변이다**(3.1의 "이름·색을 `m`에서
계산" 한 가지만 달라진다 — 관측 가능한 차이는 낙관적 체인 중첩 시에만 난다).

### 3.4 뮤테이션 1건

그룹 생성과 테이블 배정이 **한 producer** 안에 있으므로 Revision 1건이고 `cmd+Z` 한 번에 전부
원복된다. op 수는 `1(그룹 create) + N(테이블 update)`이다 — `setTableGroup`과
`clearTableGroupPosition`이 같은 테이블을 두 번 건드려도 `diffModels`는 엔티티당 update op 하나를
낸다.

`MAX_OPS_PER_MUTATION`(5000)에 걸리려면 4999개를 선택해야 하므로 **삭제 다이얼로그 같은 상한 가드는
두지 않는다.** 그 가드가 있는 곳은 연쇄 삭제(테이블+컬럼+인덱스+관계라 테이블 수의 수십 배가 된다)라
성격이 다르다.

## 4. 테스트

### `bulk-panel.test.tsx` (기존 파일에 추가)

1. 버튼 클릭 → 새 그룹이 생기고 **선택한 테이블 전원**의 `groupId`가 그 그룹이다.
2. **뮤테이션은 1건이다** — 생성과 배정이 한 Revision이어야 `cmd+Z`가 한 번에 돈다.
3. 이름이 **미사용 최소 번호**다 — `그룹1`·`그룹3`이 있으면 새 그룹은 `그룹2`.
4. 이동 대상 전원의 `groupPosition`이 `null`이다 — **옛 그룹에 있던 테이블도 포함**(3.1의 ⚠️가
   막는 것이 정확히 이 경우다).
5. `canEdit=false`면 버튼이 잠긴다.

기존 스위트가 이미 `그룹 드롭다운으로 옮기면 op 배치 한 건으로 나간다(undo 1회)`·`이미 대상 그룹에
있던 테이블의 그룹 뷰 좌표도 비운다` 같은 형태를 갖고 있다 — **그 픽스처와 단언 방식을 그대로
따른다.**

### `table-tree.test.tsx` (회귀)

6. 좌측 「그룹 추가」가 리팩터 후에도 같은 결과를 낸다 — 멤버 없는 그룹 + 자동 이름 + 그 그룹이
   선택됨. 해당 케이스가 이미 있으므로(`table-tree.test.tsx:101`·`:125`) **새로 쓰지 않고 그대로
   통과하는 것으로 확인한다.**

### 잠기지 않는 것 (명시)

`createGroupWith`가 id를 **producer 밖에서** 발급하는 계약은 어떤 테스트로도 깨지지 않는다 —
`use-model.ts`가 producer를 정확히 한 번만 부르기 때문이다. `planPasteColumnIds`와 같은 성격이고
(6절 이월 항목에 이미 있다), 억지 테스트는 만들지 않는다. 여기서는 **반환값이 필요해서** 밖일 뿐이라
안으로 옮길 유인 자체가 없다.

## 6. 이월 (구현하지 않는다)

- **흩어진 선택으로 만든 그룹은 영역이 크고 남의 테이블을 품는다**(D2의 한계). 걸리면 선택지는
  둘 — 만들기 전에 사용자가 모으거나, "선택 밖 테이블이 영역에 들어올 때만 모아 붙이는" 배치
  규칙을 새로 두거나.
- **그룹 이름을 만든 직후 자동 포커스하지 않는다.** 좌측 「그룹 추가」와 대칭을 지킨 결과다. 둘을
  함께 바꾼다면 `GroupPanel`의 이름 input에 `autoFocus`를 주는 한 곳이다.
