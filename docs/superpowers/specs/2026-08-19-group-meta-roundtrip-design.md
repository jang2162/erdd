# 덤프 머릿말로 그룹·별칭까지 왕복 복원 — 설계

- 날짜: 2026-08-19
- 선행: [덤프 머릿말 메타정보로 템플릿 왕복 복원](2026-08-18-name-meta-roundtrip-design.md)
  (`erdd:v1` 머릿말을 만든 사이클), [테이블 물리명 형식 템플릿](2026-08-17-table-name-template-design.md)
- 이월 출처: `docs/superpowers/HANDOFF.md` 6절 「템플릿·그룹 별칭 복원 — 범위 밖(설계 D2)」

⚠️ **이 설계는 직전 사이클의 D2(「부분 이름만 싣는다 — 템플릿·별칭은 싣지 않는다」)를 절반만
뒤집는다.** 그룹·별칭은 싣고 **명명 규칙 템플릿은 여전히 싣지 않는다.** D2 의 근거였던
「가져오기가 프로젝트 설정을 덮어쓰지 않는다」는 **그대로 살아 있다** — 이 사이클이 넓히는 것은
가져오기가 **이미 만들고 있는 모델 데이터**(그룹)의 출처뿐이다.

---

## 1. 목적과 범위

### 지금 무엇이 안 되는가

| 경로 | 그룹 배정 | 색 | 코멘트 | 별칭 |
|---|---|---|---|---|
| DBML 내보내기·가져오기 | ✅ `TableGroup` 블록 | ✅ | ✅ | ❌ (`alias: ''` 로 만든다) |
| DDL 내보내기·가져오기 | ❌ 아예 없다 | ❌ | ❌ | ❌ |

`planDdlImport` 의 그룹 입력은 `parsed.groups` 하나뿐이고 그것은 **DBML 파서만 채운다**
(`ImportInput = ParsedDdl & Partial<Pick<ParsedDbml, 'groups' | 'customValues'>>`).
DDL 로 내보냈다 되읽으면 그룹이 통째로 사라진다.

### 그래서 생기는 두 번째 손해 — 틀린 「건너뜀」

직전 사이클이 이름 충돌을 **만들어질 이름**(= 머릿말이 되돌린 부분) 기준으로 보게 했다. 그 결과
원본에서 그룹이 갈라 정상 공존하던 `회원.ORD` 와 `상품.ORD` 가, 가져오기가 그룹을 몰라
**뒤엣것을 건너뛴다.** 직전 사이클은 이것을 「D2 의 귀결」로 문서에 적고 경고 문구만 정확히 냈다.

그룹이 복원되면 그 건너뜀은 **틀린 판정**이 된다. 이 사이클은 그것까지 닫는다.

### 범위

- **한다**: 머릿말에 그룹 배정 + 그룹 속성(별칭·색·코멘트)을 싣는다. DDL·DBML 양쪽.
  가져오기가 그것으로 그룹을 만들고 별칭을 채운다. 충돌 판정이 그룹을 본다.
- **안 한다**: 명명 규칙 템플릿 복원(D2 의 나머지 절반), 컬럼 이름 템플릿, CLI 파일 형식 변경,
  그룹 좌표(`groupPosition`) 복원.

**서버 변경 없음. 마이그레이션 없음. CLI 변경 없음.** 웹은 한 줄이다.

## 2. 확정된 결정 (사용자 확정)

### D1. 머릿말은 그룹 배정 + 별칭까지 싣는다 — 템플릿은 싣지 않는다

**근거:** 이월 항목이 「템플릿·그룹 별칭 복원」으로 둘을 묶고 있었지만 성격이 다르다.

| | 성격 | 가져오기가 지금 하는 일 |
|---|---|---|
| 그룹·별칭 | **모델 데이터** | 이미 만든다(DBML 경로). 기계가 이미 있다 |
| 명명 규칙 템플릿 | **프로젝트 설정** | 한 번도 건드린 적 없다 |

템플릿까지 열면 가져오기가 프로젝트 설정을 바꾸는 첫 사례가 되고 미리보기·동의·충돌 처리가
통째로 따라온다. 그리고 **템플릿 복원은 왕복의 완성에 필요하지 않다** — 부분은 이미 복원되고,
템플릿은 렌더링에만 쓰인다. 받는 프로젝트에 템플릿이 없어 재내보내기 텍스트가 원본과 다른 것은
직전 설계 D2 가 이미 「결함이 아니다」로 판정했다(저장은 부분·산출은 조합).

### D2. 그룹 속성은 이름·별칭·색·코멘트를 다 싣는다

**근거:** `DdlImportGroup` 이 이미 `{name, color, comment, tablePhysicalNames, existingId}` 를
나른다 — 색·코멘트를 실을 자리를 새로 만들 필요가 없다. 이름·별칭만 실으면 DDL 왕복에서 그룹 색이
팔레트 순서대로 새로 붙어 원본과 달라지고 그룹 코멘트가 사라진다. 머릿말은 그룹 수만큼만 길어진다.

### D3. 이름이 같은 그룹이 이미 있으면 기존 값을 유지하고, **별칭이 다를 때만** 경고한다

**근거:** 가져오기가 기존 모델 엔티티를 고치지 않는 것이 현행 관례다(`existingId` 경로는 그룹을
재사용만 하고 색·코멘트를 안 건드린다). 그 관례를 지킨다.

경고를 **별칭에만** 내는 이유: 별칭은 `{그룹별칭}` 변수로 **물리명 조합에 들어가 최종 이름을
바꾼다.** 조용히 갈리면 사용자가 보는 이름이 원본과 달라지는데 이유를 알 길이 없다. 색·코멘트는
표시용이라 갈려도 이름이 안 바뀐다. 모든 차이를 경고하면 시끄러워 진짜 신호가 묻힌다.

### D4. 그룹만 쓰고 템플릿을 안 쓰는 프로젝트에도 머릿말을 낸다

직전 사이클의 D4 는 「조합 결과가 부분과 다른 테이블」만 실어 **템플릿을 안 쓰는 프로젝트의
산출물이 한 글자도 안 바뀌는 것**을 보장했다. 그룹은 템플릿과 무관하므로 그 보장을 그대로 두면
**그룹만 쓰는 프로젝트는 이번 기능이 닿지 않는다** — 기능의 절반이 죽는다.

**보장을 「그룹도 템플릿도 안 쓰는 프로젝트」로 좁힌다.**

⚠️ **대가:** 그룹을 쓰는 프로젝트는 이미 내보낸 DDL 과 새로 내보낸 DDL 이 갈린다(첫 줄에 없던
주석이 생긴다). 접기 규칙 변경 때와 같은 종류의 변화이고, 사용자 매뉴얼에 함께 적는다.

### D5. 형식은 `erdd:v2` 로 올리고 최상위를 두 구획으로 나눈다

```
-- erdd:v2 {"t":{"TB_MBR_ORD":{"p":"ORD","l":"주문","g":"회원"}},"g":{"회원":{"a":"MBR","c":"#4f46e5","n":"회원 도메인"}}}
```

**버린 대안 (1) — v1 형태를 유지하고 테이블 항목에 그룹 속성을 반복한다**
(`{"p":"ORD","l":"주문","g":"회원","ga":"MBR","gc":"#4f46e5"}`). 옛 파서가 추가 키를 무시하므로
앞뒤 호환이 되지만, **같은 그룹의 별칭·색이 테이블마다 따로 적히는 형태**가 된다. 서로 다른 값이
적힐 수 있는 구조를 만들면 읽는 쪽이 「먼저 나온 것을 쓴다」 같은 임의 규칙을 지어내야 한다.

**버린 대안 (2) — `-- erdd:groups:v1` 둘째 줄을 더한다.** 파서가 「첫 마커에서 멈춘다」라
여러 줄을 읽도록 고쳐야 하고 「머릿말은 한 줄」 계약이 깨진다.

**v1 은 계속 읽는다.** 마커로 갈리므로 이미 내보낸 덤프가 그대로 산다. 반대 방향(옛 ERDD 가
새 덤프를 읽음)은 모르는 버전 → `null` → 옛 동작으로 떨어진다 — 직전 설계 D6 이 이미 보장한다.

### D6. 충돌 판정 키를 (그룹 이름, 만들어질 부분 이름) 으로 넓힌다

| 상황 | 지금 | 바뀐 뒤 |
|---|---|---|
| 같은 그룹 · 같은 부분 | 건너뜀 | 건너뜀 (진짜 중복) |
| **다른 그룹 · 같은 부분** | **건너뜀** | **둘 다 들어온다** — 원본 그대로 |
| 한쪽만 그룹 있음 · 같은 부분 | 건너뜀 | **둘 다 들어온다** (조합 결과가 갈리므로 원본에서 공존했다) |
| 양쪽 다 그룹 없음 · 같은 부분 | 건너뜀 | 건너뜀 (키의 그룹 자리가 둘 다 빈 문자열) |

기존 모델과의 비교(`existing`)도 같은 키로 맞춘다 — 한쪽만 넓히면 「DDL 안에서는 공존하는데
모델과는 부딪힌다」는 비대칭이 생긴다.

**템플릿이 없는 프로젝트로 가져가면** 두 `ORD` 의 최종 이름이 진짜로 겹친다. 그것은 가져오기가
건너뛸 일이 아니라 `computeWarnings` 의 물리명 중복 경고가 **최종 이름 기준으로 이미 낸다**
(HANDOFF 3.16). 가져오기는 원본을 그대로 재현하고 판단은 검사에 맡긴다.

### D7. DBML 은 소스가 둘이 되고, 같은 이름이면 머릿말이 이긴다

DBML 은 `TableGroup` 블록(색·코멘트·멤버)과 머릿말을 둘 다 갖는다. 우리 산출물은 둘이 일치하지만
형식상 갈릴 수 있다. **머릿말이 이긴다** — 별칭은 머릿말에만 있고, 머릿말은 우리가 쓴 것이
확실한 반면 블록은 사람이 손댔을 수 있다. 블록에만 있는 그룹은 그대로 살린다(남이 준 DBML 은
머릿말이 없어 지금 동작 그대로다).

## 3. 구조

### 3.1 메타 모듈 (`packages/core/src/name-meta.ts`)

```ts
/** 한 테이블의 저장값(부분) + 그룹 배정. g 는 그룹에 속할 때만 있다. */
export type NameMetaEntry = { p: string; l: string; g?: string }
/** 그룹 속성. a=별칭, c=색, n=코멘트. 빈 값은 키를 생략한다. */
export type NameMetaGroup = { name: string; a?: string; c?: string; n?: string }

export type NameMeta = {
  /** 조합된 물리명(대문자 색인) → 부분 + 그룹 이름 */
  tables: Record<string, NameMetaEntry>
  /** 그룹 이름(대문자 색인) → 속성. 표시용 원문 이름은 name 이 나른다. */
  groups: Record<string, NameMetaGroup>
}
```

⚠️ **직렬화는 원문 그대로 적고 조회 키만 대문자다**(직전 설계 3.1 의 규칙을 그룹 이름에도 그대로
적용한다). `t` 의 `g` 값도 원문 그룹 이름이고, 조회할 때 대문자로 맞춘다.

⚠️ **`NameMetaGroup.name` 은 직렬화하지 않는다.** JSON 의 그룹 키가 곧 원문 이름이고
(`{"회원":{"a":"MBR"}}` — `name` 키가 따로 없다), 파서가 **키를 대문자로 색인하면서 원문 키를
`name` 에 담는다**. 그래서 이름을 만들 때(`tableGroups[id].name`) 대문자로 뭉개지지 않는다.

- `serializeNameMeta(meta, prefix)` — 실을 것이 하나도 없으면(`tables` 와 `groups` 가 둘 다 비면)
  `null`. **한 줄**이어야 한다는 계약은 그대로다.
- `parseNameMeta(raw)` — 마커로 v1/v2 를 가른다.
  - `erdd:v2` → 위 형태로 읽는다
  - `erdd:v1` → `{tables: {...}, groups: {}}` 로 승격해 읽는다(옛 덤프 호환)
  - 형태가 안 맞는 것은 전부 `null` — **예외를 던지지 않는다**(직전 D6)

### 3.2 머릿말 빌더를 한 자리로 합친다

지금 `ddl.ts` 와 `dbml.ts` 에 **몸통이 같은 `buildNameMeta` 가 각각 있다.** 「내보내는 테이블
목록이 서로 달라 공유하지 않는다」는 주석이 붙어 있지만, 그 목록은 **이미 인자로 받는다**
(`buildNameMeta(model, tables, rules)`). 이번에 몸통이 그룹 수집만큼 커지므로 `name-meta.ts` 로
옮겨 하나로 만든다.

```ts
export function buildNameMeta(model: ProjectModel, tables: Table[], rules: NamingRules): NameMeta
```

싣는 규칙:
- **`tables` 항목** — 조합 ≠ 부분이거나 `groupId !== null` 인 테이블. 항목은 늘 `{p, l}` 을 싣고
  그룹이 있으면 `g` 를 더한다(파서가 균일하게 읽게).
- **`groups` 항목** — 위에서 실제로 실린 테이블이 속한 그룹만. 빈 별칭·빈 코멘트는 키를 생략한다.

### 3.3 가져오기 배선 (`packages/core/src/ddl-import.ts`)

**(a) 그룹 목록을 두 소스에서 모은다.**

```
머릿말 그룹(D7 우선) ∪ parsed.groups 중 머릿말에 없는 이름만
```

머릿말의 멤버십은 테이블 → 그룹 이름이고 블록은 그룹 → 테이블 목록이다. 둘을 같은
`DdlImportGroup[]` 로 모은다. 멤버는 **살아남은 테이블만** 담고(현행 그대로) 이름은
`t.physicalName`(= 복원된 부분)이다.

**(b) `DdlImportGroup` 에 `alias: string` 을 더한다.** 없으면 빈 문자열.

**(c) 충돌 판정 키를 넓힌다(D6).** 지금 `existing` · `claimed` 는 `upper(부분 이름)` 한 겹이다.
그룹 이름과 부분 이름을 **NUL 문자(`'\u0000'`)로 이어** 한 키로 만든다 — 그룹 이름은 사용자가 자유롭게
쓰는 문자열이라 `.` `_` 같은 흔한 구분자를 쓰면 서로 다른 (그룹, 이름) 짝이 같은 키가 될 수 있다
(`A_B` + `C` 와 `A` + `B_C`). NUL 은 어느 이름에도 들어갈 수 없다.
모델 쪽 키는 `model.tables[].groupId` → `model.tableGroups[].name` 으로 환산한다.

⚠️ 그룹 이름을 못 찾으면(가져오기가 만들 새 그룹) 머릿말의 그룹 이름을 그대로 쓴다 — 아직 id 가
없으므로 **이름이 유일한 좌표**다.

**(d) `group-conflict` 경고를 더한다(D3).** `DdlImportWarning['kind']` 에 추가한다 —
HANDOFF 3.14 「새 `Warning['kind']` 를 추가할 때」 체크리스트를 따른다.

문구: 「머릿말의 별칭 MBR 과 기존 그룹의 별칭 MB 가 달라 기존 값을 유지합니다」
(`target` 은 그룹 이름).

### 3.4 적용 배선 (`apps/web/src/editor/ddl-import-edits.ts`)

`tableGroups[groupId] = { …, alias: '' }` 한 자리를 `alias: g.alias` 로 바꾼다. **이것이 웹의
전부다.** 기존 그룹을 쓰는 경로(`existingId !== null`)는 지금처럼 아무것도 안 고친다.

### 3.5 내보내기 배선

`ddl.ts` · `dbml.ts` 의 `buildNameMeta` 호출을 `name-meta.ts` 의 것으로 바꾼다. 머릿말을 내는
자리 자체는 그대로다.
