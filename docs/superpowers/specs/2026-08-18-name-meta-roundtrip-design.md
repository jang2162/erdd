# 덤프 머릿말 메타정보로 템플릿 왕복 복원 — 설계

**작성:** 2026-08-18 / **상태:** 사용자 확정 / **마이그레이션:** 없음 /
**core 변경:** 메타 모듈 신설 + 내보내기 2자리 + 파서 2자리 + 플래너 1자리 ·
**server·CLI·web 변경:** 없음

---

## 1. 목적과 범위

**내보낸 DDL·DBML 을 되읽으면 접두가 통째로 물리명에 박히던 것을 고친다.** 템플릿이 걸린 프로젝트에서
`TB_MBR_ORD` 를 내보내고 다시 가져오면 지금은 `physicalName = 'TB_MBR_ORD'` 가 되고, 다시 내보내면
`TB_MBR_TB_MBR_ORD` 가 된다. 파일 머리에 **부분 이름을 적은 주석 한 줄**을 실어 추측 없이 되돌린다.

⚠️ **이 설계는 물리명 템플릿 사이클의 D2(「역분해하지 않는다, 왕복이 깨진 채로 둔다」)를 뒤집는다.**
그 사이클이 `ddl-import.test.ts` 에 심어 둔 「왕복이 깨진다」 고정 테스트가 **바로 이 재검토를 강제하려던
장치**다. 그 케이스는 이 사이클에서 둘로 갈린다(4절).

역분해가 원리적으로 모호하다는 D2 의 근거는 **여전히 유효하다** — `TB_MBR_ORD_DTL` 을
`TB_{그룹별칭}_{물리명}` 으로 가르면 「그룹=MBR, 부분=ORD_DTL」과 「그룹=MBR_ORD, 부분=DTL」이 둘 다
문자열로 맞다. 이 설계는 **역분해를 하지 않는다.** 내보낼 때 정답을 적어 두고 읽을 때 그대로 쓴다.

**범위 안**

| 대상 | 하는 일 |
|---|---|
| `packages/core/src/name-meta.ts` (신설) | 머릿말 직렬화 · 파싱 |
| `packages/core/src/ddl.ts` | 머릿말 한 줄 앞에 붙이기 |
| `packages/core/src/dbml.ts` | 〃 (접두만 `//`) |
| `packages/core/src/ddl-parse.ts` | 원문 머리에서 메타를 읽어 `ParsedDdl` 에 싣기 |
| `packages/core/src/dbml-parse.ts` | 〃 (`ParsedDbml`) |
| `packages/core/src/ddl-import.ts` | 부분 복원 — **DDL·DBML 공용 플래너라 한 자리** |

**범위 밖 (건드리지 않는다)**

- **템플릿·그룹 별칭 복원** — 가져오기는 프로젝트 설정을 건드리지 않는다(D2).
- **컬럼** — 컬럼에는 템플릿이 없다.
- **CLI 파일 포맷·클립보드** — 부분을 그대로 싣는 기존 경계 그대로.
- **server·web** — 변경 없음. 이 사이클은 core 안에서 끝난다.

## 2. 확정된 결정 (사용자 확정)

### D1. 메타는 덤프 머릿말 한 줄에 싣는다 — 테이블 코멘트가 아니라

```
-- erdd:v1 {"TB_MBR_ORD":{"p":"ORD","l":"주문"}}
CREATE TABLE TB_MBR_ORD ( … );
COMMENT ON TABLE TB_MBR_ORD IS '주문';
```

**근거:** ⚠️ **DDL 코멘트는 실제 DB 에 저장된다.** `COMMENT ON TABLE` 을 실행하면 그 문자열이 그
데이터베이스의 메타데이터가 되어 DBeaver·DataGrip·`\d+` 등 모든 도구에 그대로 보인다. 우리 내부
JSON 을 거기 넣으면 사용자의 DB 를 오염시킨다. **DBML note 는 문서 파일일 뿐이라 성격이 다르다** —
커스텀 값 JSON 꼬리(`buildDbmlNote`)가 거기 들어가 있는 것은 그래서 괜찮았다.

머릿말 주석은 **실행돼도 DB 에 안 남는다.**

⚠️ **수용하는 대가:** `CREATE TABLE` 한 문장만 잘라 붙여넣으면 머릿말이 없어 지금 동작(통째로 부분)으로
떨어진다. DB 코멘트를 깨끗하게 유지하는 것과 맞바꾼 것이다.

### D2. 부분 이름만 싣는다 — 템플릿·별칭은 싣지 않는다

`{조합된 물리명: {물리 부분, 논리 부분}}` 만 싣는다.

**근거:** 가져오기가 **프로젝트의 명명 규칙과 그룹을 덮어쓰지 않는다.** 지금까지 가져오기가 건드린
적 없는 영역이고, 열면 미리보기·충돌 처리가 통째로 늘어난다.

| 가져가는 곳 | 결과 |
|---|---|
| 같은 프로젝트(템플릿·그룹 그대로) | `ORD` / `주문` — **완전한 왕복** |
| 템플릿이 없는 다른 프로젝트 | `ORD` / `주문` 으로 깔끔하게 들어온다. 다시 내보내면 `ORD` |

두 번째 줄이 「텍스트가 원본과 다르다」는 것은 **결함이 아니다.** 모델(부분)은 보존되고 렌더링은 그
프로젝트의 설정을 따른다 — 그것이 저장은 부분·산출은 조합이라는 D1(물리명 사이클)의 귀결이다.

### D3. DDL 과 DBML 을 함께 닫는다

메타 직렬화/파싱 모듈 하나를 둘이 공유하고 **주석 접두만 갈린다**(`--` / `//`).

**근거:** 두 파서가 같은 구조다 — 둘 다 파싱 전에 주석을 걷어낸다
(`ddl-parse.ts:35-68`, `dbml-parse.ts:73,504`). 증분 비용은 내보내기 한 자리 + 파서 한 자리다.
**`dbml-roundtrip.test.ts` 가 이 저장소의 대표 왕복 스위트인데** DDL 만 고치면 그쪽만 깨진 채 남는다.

### D4. 템플릿이 하나도 안 걸렸으면 머릿말을 아예 내지 않는다

**근거:** 조합 == 부분이라 실을 것이 없다. 그리고 그래야 **기존 산출물이 바이트 단위로 그대로**다 —
템플릿을 안 쓰는 프로젝트의 DDL·DBML 이 한 글자도 안 바뀌고 기존 왕복 테스트가 하나도 안 깨진다.
**이 설계의 안전장치다.**

### D5. 논리명은 메타가 코멘트를 이긴다

코멘트에는 **조합된** 논리명이 들어 있고(`SALES_회원`) 메타에는 부분이 있다(`회원`). 논리명은 메타를
쓰고, **설명(` - ` 뒤)은 코멘트에서 그대로** 가져온다.

**근거:** 논리명 템플릿 사이클이 코멘트에 조합 논리명을 넣도록 바꿨다. 메타가 없으면 지금처럼
코멘트 → 사전 순으로 떨어진다.

### D6. 깨진 입력은 전부 무시하고 현행 동작으로 떨어진다 — 예외를 던지지 않는다

JSON 파싱 실패 · 모르는 버전 · 키 불일치(사용자가 DDL 의 테이블 이름을 손으로 고친 경우) · 남의 DDL.
전부 「메타 없음」으로 취급한다.

**근거:** 템플릿의 「알 수 없는 변수는 빈 값」과 같은 철학이다. 가져오기는 남이 준 파일을 다루는
경로라 한 글자 때문에 통째로 죽으면 안 된다.

⚠️ **메타를 검증하지 않는다** — 검증하려면 조합 이름을 재계산해야 하는데 **DDL 가져오기 시점에는 그룹
배정 정보가 없다**(그룹은 DBML 에만 있다). 재계산이 원리적으로 불가능하므로 메타를 그대로 믿는 것
말고 선택지가 없다. 키가 안 맞으면 자연히 「메타 없음」으로 떨어진다.

## 3. 구조

### 3.1 메타 모듈

```ts
// packages/core/src/name-meta.ts
/** 한 테이블의 저장값(부분). p=물리 부분, l=논리 부분. 키를 짧게 두어 머릿말이 길어지지 않게 한다. */
export type NameMetaEntry = { p: string; l: string }
/**
 * 조합된 물리명 → 부분.
 * ⚠️ **직렬화는 조합 이름을 원문 그대로 적고, 조회는 `upper()` 로 한다.** 대문자로 적어 두면
 * lower_snake 프로젝트의 머릿말이 실제 이름과 달라 보인다. 파싱 직후 `upper()` 키로 다시 색인한다.
 */
export type NameMeta = Record<string, NameMetaEntry>

/** 머릿말 한 줄. 실을 것이 없으면 null(D4). */
export function serializeNameMeta(meta: NameMeta, prefix: '--' | '//'): string | null

/** 원문 머리에서 메타를 읽는다. 없거나 깨졌으면 null(D6). */
export function parseNameMeta(raw: string): NameMeta | null
```

형식: `<접두> erdd:v1 <JSON>` — **한 줄**이다(`JSON.stringify` 는 줄바꿈을 내지 않는다). 한글은 SQL·
DBML 주석에 그대로 들어간다.

### 3.2 파싱은 파일 머리에서만 훑는다

**첫 비주석·비공백 줄이 나오면 멈춘다.** 중간에 섞인 마커를 줍지 않고 스캔 비용이 상수다.
두 파서 모두 `stripComments` 로 주석을 걷어내므로 **그 전에** 원문을 한 번 보는 패스를 넣는다
(`parseDdl(text, dialect)`·`parseDbml(text)` 둘 다 원문 문자열을 받는다).

`ParsedDdl` 과 `ParsedDbml` 에 각각 `nameMeta?: NameMeta` 를 더한다.

### 3.3 가져오기 배선 — 한 자리

`ddl-import.ts:205` 의 `physicalName: t.name` 이 **조합 이름을 통째로 부분에 넣던 자리**다.

```ts
const m = parsed.nameMeta?.[upper(t.name)]
// physicalName: m?.p ?? t.name
// logicalName:  m?.l ?? named.logicalName      ← 설명은 named.comment 를 그대로 쓴다(D5)
```

⚠️ **`planDdlImport` 는 DDL·DBML 공용 플래너다**(`ImportInput = ParsedDdl & Partial<Pick<ParsedDbml,
'groups' | 'customValues'>>`). **여기 한 번 배선하면 두 포맷이 함께 닫힌다.**

⚠️ 키는 `upper()` 로 맞춘다 — DDL 식별자는 인용·대소문자가 갈릴 수 있고, 이 파일이 이미 모든 색인에
`upper()` 를 쓴다.

### 3.4 내보내기 배선 — 두 자리

`generateDdl`·`generateDbml` 이 각자 **자기가 실제로 내보내는 테이블 목록으로** 메타를 만든다
(0컬럼·빈 이름으로 제외된 테이블은 메타에도 없어야 한다). 둘 다 이미 `model`·`rules` 를 갖고 있어
조합 이름과 부분을 모두 계산할 수 있다.

DBML 은 `Project { … }` 블록보다 **앞**에 둔다 — 머릿말은 파일의 첫 줄이어야 3.2 의 스캔에 걸린다.

## 4. 테스트

**core — 메타 모듈**
- 직렬화 → 파싱 왕복
- 실을 것이 없으면 `null`(D4)
- 깨진 JSON · 모르는 버전 · 마커 없음 → `null`(D6)
- **첫 비주석 줄 뒤의 마커는 안 줍는다**(3.2)

**core — 왕복 (이 사이클의 급소)**
- ⚠️ **`ddl-import.test.ts` 의 「왕복이 깨진다」 고정 테스트가 둘로 갈린다:**
  - **메타가 있으면** 부분이 복원된다 — `physicalName === 'ORD'`, `logicalName === '주문'`
  - **메타가 없으면**(머릿말을 떼어낸 남의 DDL) 지금처럼 통째로 부분이 된다 — 옛 케이스를 그 형태로 남긴다
- 두 번 왕복해도 `TB_MBR_TB_MBR_ORD` 가 안 나온다
- DBML 도 같은 두 짝
- ⚠️ **템플릿이 없으면 산출물이 한 글자도 안 바뀐다**(D4) — 기존 왕복 스위트가 그대로 통과하는 것으로
  확인되지만, 「머릿말이 안 나간다」를 직접 단언하는 케이스도 둔다

**core — 배선**
- 논리명은 메타가 코멘트를 이기고 **설명은 코멘트에서 온다**(D5)
- 키가 안 맞으면 현행 동작으로 떨어진다(D6)
- 내보내기에서 제외된 테이블은 메타에 없다(3.4)

**잠기지 않는 것 (명시)**
- **`CREATE TABLE` 한 문장만 잘라 붙였을 때 머릿말이 없는 것**은 D1 이 수용한 대가이지 버그가 아니다.
  「메타가 없으면 현행 동작」 케이스가 그 상황을 그대로 덮는다 — 별도 케이스를 만들지 않는다.
